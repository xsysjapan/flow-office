# 30. 経費精算ユースケース (UC-X001~)

通勤費・業務交通費・その他経費(宿泊費・会食・消耗品等)を単一の「経費精算」ドメインで
扱う。通勤費であっても専用の自動計算ドメインを持たず、勤怠実績はあくまで入力補助・承認時の
突合せ表示に使う参考情報とし、経費精算のデータモデル自体を交通費向けに特化させない。

## 前提: 通勤費は独立ドメインではない

- `commuting_profiles` のような通勤費専用テーブルや、月次自動計算・自動確定の専用
  Command/Eventは持たない。
- 通勤費も業務交通費も、他のその他経費と同じ `expense_claims` / `expense_items` に
  本人が都度入力する。
- 勤怠実績 (`attendance_days.work_location_type` など) は「この日は出社/客先訪問と
  記録されています」という **入力補助の候補提示** と、承認画面での **突合せ表示** の
  2箇所にのみ使う。勤怠データから金額を自動算出したり、経費明細を勤怠側の確定情報として
  扱ったりしない (docs/03-architecture.md 原則9・原則11と同じ考え方: 参照系のロジックが
  正データ側の計算・確定を汚染しない)。

## マスタ

### UC-X001: 経費区分を設定する

1. 管理者が経費区分マスタ (`expense_categories`) を開く
2. 区分コード・名称 (例: 交通費・宿泊費・会食・消耗品・その他) を登録する
3. 入力方式 (`entry_mode`: `batch` 複数件まとめて入力 / `single` 都度1件ずつ入力) を設定する。
   交通費は`batch`、会食・宿泊・消耗品・その他は`single`が既定
4. 証憑タイプの既定値 (`fact_reference_available` / `receipt_required` / `receipt_optional`)
   を設定する
5. レシート添付が必須となる金額しきい値を設定する (任意)
6. 承認ルール (一定額以下は上長承認を省略する等) を設定する
7. 保存する

区分ごとの違い (入力方式を含む) はすべてマスタ設定であり、区分追加のためにコードを変更しない。
`entry_mode`によって、社員が経費区分を選んだ直後にどの入力フォームを開くか (UC-X004a〜d) が
決まる。

### UC-X002: 個人の移動区間テンプレートを登録する

1. 社員がよく使う移動区間 (例: 自宅最寄り駅 ⇔ 会社) を登録する画面を開く
2. 出発地・到着地・交通手段・既定金額・対象の経費区分を入力する
3. スコープは自動的に「個人 (`personal`)」になる
4. 保存する。以後、本人の経費明細入力画面で候補として選べる

### UC-X003: 全社共有の移動区間テンプレートを登録する

1. 経理・管理者が全社共有テンプレート管理画面を開く
2. 出発地・到着地・交通手段・既定金額・対象の経費区分を入力する (例: 本社 ⇔ A社)
3. スコープを「全社共有 (`company`)」として保存する
4. 全社員の経費明細入力画面で候補として表示されるようになる

個人用・全社共有は `expense_route_templates` の `scope` の違いだけで、テーブル構造や
振る舞いを分けない。編集権限は個人用は本人のみ、全社共有は経理・管理者のみ。

## 明細入力

### UC-X004: 経費区分を選んで入力を開始する

1. 社員が「経費を精算する」を開く
2. **対象期間は聞かない。** まず経費区分 (`expense_categories`、例: 交通費・会食・宿泊費・
   消耗品・その他) を選ぶ
3. 選んだ区分の `entry_mode` によって、以降の入力フォームが自動的に切り替わる
   - `batch` (交通費) → UC-X004a (表形式・移動経路・テンプレートのいずれかでまとめて入力)
   - `single` (会食・宿泊・消耗品・その他) → UC-X004b〜d (その場で1件分を直接入力)
4. 明細を1件以上保存すると、`expense_claims` (申請ヘッダー) がこの時点で暗黙に作成される。
   ユーザーが期間を指定する操作は存在しない
5. `expense_claims.period_from`/`period_to` は保存された明細の `usage_date` の最小値・最大値
   から**自動算出される表示用の値**であり、正データとしてユーザーに入力させない (原則2:
   Projectionは再生成可能な派生データ)。単発区分で1件だけ保存すればその日1日が期間になり、
   交通費で複数日分入力すればその期間が自動的に広がる

### UC-X004a: 交通費をまとめて入力する (旧UC-X006〜X008相当)

1. 対象日を選ぶと、その日の勤怠実績 (`work_location_type`: 出社・客先訪問・出張等) が
   参考情報として表示される (勤怠は入力補助のみ、金額の自動算出には使わない)
2. 次のいずれかの方法で複数の明細をまとめて入力する
   - **表形式入力**: 日付・経費区分・金額・内容を1行ずつ入力する。前の行を複製する、
     複数行をまとめて貼り付ける、行を並べ替える
   - **移動経路入力**: 自宅・会社・訪問先を順に地点として追加し、区間ごとに交通手段・金額を
     入力する。徒歩・私用の区間は「精算対象外」にする
   - **テンプレートから生成**: 個人・全社共有の移動区間テンプレート (UC-X002/UC-X003) を選び、
     カレンダーから対象日を複数選択して「まとめて追加」する。金額はテンプレートの既定値が
     初期値として入るが明細ごとに編集できる
3. いずれの方法でも、経路情報は「出発地 → 到着地 (交通手段)」という所定フォーマットの
   1行テキストに整形され、`expense_items.description` (内容) に格納される。構造化した
   出発地・到着地・交通手段の列は`expense_items`には持たない (原則: データを特化させない)
4. 保存すると複数の `expense_items` が一度に作成される

### UC-X004b: 会食・接待費を入力する

1. 利用日・取引先 (店名)・参加者氏名・参加人数・金額・内容を入力する
   (参加人数は税務上、1人あたり金額の算出根拠になるため入力必須とする)
2. 入力内容は「{内容} ({取引先}、{人数}名: {参加者})」のような所定フォーマットに整形して
   `description` に格納する (フォーマットの詳細は実装時に確定する)
3. レシートを1件以上添付する (会食・接待は原則レシート必須)
4. 明細を保存する

### UC-X004c: 宿泊費を入力する

1. 利用日・宿泊先名・金額・内容を入力する
2. 「{宿泊先名} - {内容}」のような所定フォーマットに整形して`description`に格納する
3. レシートを1件以上添付する
4. 明細を保存する

### UC-X004d: 消耗品・その他の経費を入力する

1. 利用日・取引先 (店名等)・金額・内容を入力する
2. 「{取引先} - {内容}」のような所定フォーマットに整形して`description`に格納する
3. 経費区分のレシート必須しきい値 (UC-X001) に応じてレシートを添付する
4. 明細を保存する

### UC-X009: 定期区間との重複を自己申告する

1. 社員が交通費明細を入力する際、その区間が通勤定期券区間と重複する可能性がある場合
   「定期券区間を含む」を選択する
2. 定期券控除額を入力する
3. 会社負担額 (`amount - commuting_deduction_amount`) が自動計算される
4. 承認者は明細一覧で控除自己申告の有無を確認できる

初期段階では自動判定を行わず自己申告に委ねる。将来、経路検索サービスと連携して
自動控除する場合も、判定ロジックの追加先は経費精算のCommandHandlerであり、
明細のデータ構造は変更しない。

### UC-X013: 同じ申請にさらに明細を追加する (任意)

1. UC-X004a〜dのいずれかで明細を1件 (または複数件) 保存した後、「この申請にさらに明細を
   追加する」を選べる
2. 経費区分を問わず追加できる (例: 出張の宿泊費と交通費を同じ申請にまとめる)
3. 追加しない場合は、そのままUC-X010 (申請) に進む

無理に1申請1区分に限定しない。ただし既定の入り口は「区分を選ぶ→その場で入力→すぐ申請」の
単発フローであり、まとめるかどうかは申請者の任意選択とする。

## 申請・承認

### UC-X010: 経費精算を申請する

1. 社員が明細一覧 (1件以上) を確認する。対象期間は明細の利用日から自動表示されるだけで、
   ここで編集する項目ではない
2. 明細を追加・修正・削除する
3. 承認者を指定する (固定ルートまたは都度指定、原則5)
4. 申請する。`expense_claims.status` が申請中になる
5. 承認者へ通知する

### UC-X011: 経費精算を承認する (勤怠実績との突合せ表示)

1. 承認者が申請一覧を開く
2. 各明細について、`fact_reference_id` が指す勤怠実績・予定・出張申請の内容を
   並べて表示する (例: 「7/4 客先訪問と記録あり」)
3. 突合せ結果に矛盾があれば差戻す (勤怠側のデータは書き換えない)
4. 問題なければ承認する
5. `expense_categories` の承認ルールにより、しきい値以下の区分は承認を1段階省略できる

### UC-X012: 経費精算のバックオフィス処理

1. 経理担当者が承認済み経費精算を確認する (UC-B004の対象を全経費区分に拡張)
2. 領収書 (添付がある明細のみ)・金額・用途・勘定科目を確認する
3. 不備があれば差戻す
4. 問題なければ支払予定にする
5. 会計CSVまたは振込CSVを出力する
6. 支払後に完了にする

`backoffice_tasks.task_type` は経費精算1種類のままでよく、区分ごとに種別を分けない
(勘定科目のマッピングは区分マスタ側の設定で吸収する)。

## 実装上のポイント

- 通勤費・業務交通費・その他経費は `expense_categories` の値が違うだけで、
  データモデル・Command/Event・承認フロー・バックオフィス処理はすべて共通。
- **申請の入り口は「対象期間の指定」ではなく「経費区分の選択」。** `expense_claims`は
  ユーザーが期間を入力して作成するものではなく、明細を1件保存した時点で暗黙に作成される。
  `period_from`/`period_to`は明細の`usage_date`の最小値・最大値から算出する派生値として
  Projector側で保持し、ユーザー入力欄としては公開しない (原則2)。
- `expense_categories.entry_mode` (`batch`/`single`) によって、区分選択直後にどの入力
  フォームを開くかを切り替える。区分が増えても`entry_mode`の値を設定するだけでよく、
  フロントエンド側の分岐ロジックを増やさない。
- 会食・宿泊・消耗品等の`single`区分も、交通費と同じく最終的には`expense_items.description`
  1項目に整形済みテキストを格納する。区分ごとの入力しやすさは**フロントエンドの入力フォームの
  違いだけで実現し、バックエンドのデータ構造は増やさない** (交通費の「出発地 → 到着地
  (交通手段)」と同じパターン)。
- 勤怠実績への参照は「入力補助」「承認時の突合せ表示」に限定し、経費明細の金額計算・
  確定判定には使わない。
- `expense_route_templates` は個人用・全社共有をスコープの違いとして1テーブルで表現し、
  マスタCRUDのみで運用する (Command/Eventの対象にしない)。
- 定期券区間の重複判定は初期段階では自己申告とし、将来の自動判定もCommandHandler側の
  ロジック拡張として吸収し、明細のデータ構造は変えない。
- バックオフィス処理は既存のUC-B004 (経費精算) パターンをそのまま経費区分横断で使う。
