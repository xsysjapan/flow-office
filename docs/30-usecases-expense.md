# 30. 経費精算ユースケース (UC-X001~)

通勤費・業務交通費・その他経費(宿泊費・会食・消耗品等)を単一の「経費精算」ドメインで
扱う。通勤費であっても専用の自動計算ドメインを持たず、勤怠実績はあくまで入力補助・承認時の
突合せ表示に使う参考情報とし、経費精算のデータモデル自体を交通費向けに特化させない。

## 前提: 通勤費は独立ドメインではない

- `commuting_profiles` のような通勤費専用テーブルや、月次自動計算・自動確定の専用
  Command/Eventは持たない。
- 通勤費も業務交通費も、他のその他経費と同じ `expense_claims` / `expense_items` に
  本人が都度入力する。
- 勤怠実績 (`attendance_days.work_location_type` など) は「この日は出社/客先訪問と
  記録されています」という **入力補助の候補提示** と、承認画面での **突合せ表示** の
  2箇所にのみ使う。勤怠データから金額を自動算出したり、経費明細を勤怠側の確定情報として
  扱ったりしない (docs/03-architecture.md 原則9・原則11と同じ考え方: 参照系のロジックが
  正データ側の計算・確定を汚染しない)。

## マスタ

### UC-X001: 経費区分を設定する

1. 管理者が経費区分マスタ (`expense_categories`) を開く
2. 区分コード・名称 (例: 交通費・宿泊費・会食・消耗品・その他) を登録する
3. 入力方式 (`entry_mode`: `batch` 交通費専用のまとめ入力ツール(表形式・移動経路・
   テンプレート)を使う / `single` 区分専用の1件入力フォームを使う) を設定する。
   交通費は`batch`、会食・宿泊・消耗品・その他は`single`が既定。**`single`は「1件しか
   入力できない」という意味ではなく、区分専用フォームを続けて何度でも使って複数件を
   まとめて入力できる**(例: 出張で複数のホテル代・複数店舗での消耗品購入をまとめて入力)。
   区分ごとに用意する専用のバッチ入力ツールを持たないだけで、連続入力自体は妨げない
4. 証憑タイプの既定値 (`fact_reference_available` / `receipt_required` / `receipt_optional`)
   を設定する
5. レシート添付が必須となる金額しきい値を設定する (任意)
6. 承認ルール (一定額以下は上長承認を省略する等) を設定する
7. 保存する

区分ごとの違い (入力方式を含む) はすべてマスタ設定であり、区分追加のためにコードを変更しない。
`entry_mode`によって、社員が経費区分を選んだ直後にどの入力フォームを開くか (UC-X004a〜d) が
決まる。

### UC-X002: 入力プリセットを登録する

交通費専用だった移動区間テンプレート (`expense_route_templates`) は廃止し、経費全体で
共通の入力プリセット (`expense_entry_presets`) に一本化した。プリセットは特定の区分に
限定されず、1件または複数件の経費明細の下書き (区分・内容の初期値・金額の初期値・
支払方法の初期値) を定義する。

1. 社員がよく使う入力パターン (例: 自宅 ⇔ 会社の電車代、深夜タクシー、技術書購入) を
   登録する画面を開く
2. 名称・説明・作成する明細 (区分ごとに内容/金額/支払方法の初期値) を入力する
3. 公開範囲 (`visibility`) を選ぶ。個人用 (`personal`) は本人のみ編集・利用でき、
   全社共有 (`company`) ・システム標準 (`system`) は経理・管理者のみ登録できるが
   全社員が利用できる
4. 保存する。以後、対象区分を選んだ経費明細入力画面で候補として表示される

`visibility`の違いだけでテーブル構造や振る舞いを分けない。プリセットはユーザーに任意の
コード・SQL・外部API呼び出しを持たせず、単純なデータ定義 (下書きの初期値) に限定する。

### UC-X003: 全社共有・システム標準の入力プリセットを登録する

UC-X002と同じ画面・同じAPIで、`visibility`を`company`または`system`にして保存する
(経理・管理者のみ操作可能)。個別のテーブル・画面は用意しない。

## 明細入力

### UC-X004: 経費区分を選んで入力を開始する

1. 社員が「経費を精算する」を開く
2. **対象期間は聞かない。** まず経費区分 (`expense_categories`、例: 交通費・会食・宿泊費・
   消耗品・その他) を選ぶ
3. 選んだ区分の `entry_mode` によって、以降の入力フォームが自動的に切り替わる
   - `batch` (交通費) → UC-X004a (表形式・移動経路・テンプレートのいずれかでまとめて入力)
   - `single` (会食・宿泊・消耗品・その他) → UC-X004b〜d (その場で1件分を直接入力)
4. 明細を1件以上保存すると、`expense_claims` (申請ヘッダー) がこの時点で暗黙に作成される。
   ユーザーが期間を指定する操作は存在しない
5. `expense_claims.period_from`/`period_to` は保存された明細の `usage_date` の最小値・最大値
   から**自動算出される表示用の値**であり、正データとしてユーザーに入力させない (原則2:
   Projectionは再生成可能な派生データ)。単発区分で1件だけ保存すればその日1日が期間になり、
   交通費で複数日分入力すればその期間が自動的に広がる

### UC-X004a: 交通費をまとめて入力する (プリセット入力に一本化)

交通費専用の移動経路入力・テンプレートからのカレンダー生成機能は廃止し、経費全体で共通の
入力プリセット (UC-X002) による下書き生成 + 表形式レビューに一本化した。

1. 対象日を選ぶと、その日の勤怠実績 (`work_location_type`: 出社・客先訪問・出張等) が
   参考情報として表示される (勤怠は入力補助のみ、金額の自動算出には使わない)
2. この区分 (交通費) に関係する入力プリセットが「プリセットから追加」に一覧表示される。
   クリックするとプリセットの定義のうち**選択中の区分に一致する明細だけ**が下書き行として
   追加される (利用日は毎回異なるため空欄のまま追加され、以後の手順で入力する)。
   出張プリセットのように複数区分にまたがるプリセットでも、交通費を選んでいる間に宿泊費の
   行が混ざることはない。他の区分の明細を持つプリセットにはその件数を注記し、区分を切り替えて
   同じプリセットを選び直すことで同じ申請に追加できる
3. プリセットにない移動や、細かい調整は表形式入力で直接行を追加・編集する。日付・経費区分・
   金額・内容を1行ずつ入力する。前の行を複製する、複数行をまとめて貼り付ける、行を並べ替える
   こともできる
4. 経路情報を入力する場合は「出発地 → 到着地 (交通手段)」という所定フォーマットの1行
   テキストとして `expense_items.description` (内容) に入力する。構造化した出発地・
   到着地・交通手段の列は`expense_items`には持たない (原則: データを特化させない)
5. 保存すると複数の `expense_items` が一度に作成される

### UC-X004b: 会食・接待費を入力する

1. 利用日・取引先 (店名)・参加者氏名・参加人数・金額・内容を入力する
   (参加人数は税務上、1人あたり金額の算出根拠になるため入力必須とする)
2. 入力内容は「{内容} ({取引先}、{人数}名: {参加者})」のような所定フォーマットに整形して
   `description` に格納する (フォーマットの詳細は実装時に確定する)
3. レシートを1件以上添付する (会食・接待は原則レシート必須)
4. 明細を保存する。**フォームはクリアされるだけで、続けて次の会食明細を同じ画面から
   追加できる**(例: 出張中に複数回の会食があった場合、都度この手順を繰り返す)

### UC-X004c: 宿泊費を入力する

1. 利用日・宿泊先名・金額・内容を入力する
2. 「{宿泊先名} - {内容}」のような所定フォーマットに整形して`description`に格納する
3. レシートを1件以上添付する
4. 明細を保存する。**続けて次の宿泊明細を追加できる**(例: 出張中に複数のホテルに
   泊まった場合、都度この手順を繰り返す)

### UC-X004d: 消耗品・その他の経費を入力する

1. 利用日・取引先 (店名等)・金額・内容を入力する
2. 「{取引先} - {内容}」のような所定フォーマットに整形して`description`に格納する
3. 経費区分のレシート必須しきい値 (UC-X001) に応じてレシートを添付する
4. 明細を保存する。**続けて次の明細を追加できる**(例: 複数店舗で消耗品を購入した場合、
   都度この手順を繰り返す)

いずれも「1件保存→フォームがリセットされ次の1件を入力」という単純な繰り返しであり、
交通費のような専用のまとめ入力ツール(表形式・貼り付け等)は持たない。件数が多い場合の
効率化(表形式化等)は今回のスコープ外とし、必要になった時点で追加する。

### UC-X009: 定期区間との重複を自己申告する

1. 社員が交通費明細を入力する際、その区間が通勤定期券区間と重複する可能性がある場合
   「定期券区間を含む」を選択する
2. 定期券控除額を入力する
3. 会社負担額 (`amount - commuting_deduction_amount`) が自動計算される
4. 承認者は明細一覧で控除自己申告の有無を確認できる

初期段階では自動判定を行わず自己申告に委ねる。将来、経路検索サービスと連携して
自動控除する場合も、判定ロジックの追加先は経費精算のCommandHandlerであり、
明細のデータ構造は変更しない。

### UC-X013: 同じ申請に別の経費区分の明細を追加する (任意)

同一区分の明細を連続入力する操作はUC-X004b〜dの中に標準機能として含まれる (上記参照)。
UC-X013はそれとは別に、**異なる経費区分をまたいで**同じ申請にまとめたい場合の操作を指す。

1. 明細を1件以上保存した後、「別の区分の明細を追加する」を選ぶ
2. UC-X004に戻り、別の経費区分を選んで入力する (例: 出張の交通費と宿泊費を同じ申請にまとめる)
3. まとめない場合は、そのままUC-X010 (申請) に進む

無理に1申請1区分に限定しないが、既定の流れは「区分を選ぶ→その場で(必要なら複数件)入力→
すぐ申請」であり、複数区分をまとめるかどうかは申請者の任意選択とする。

## 申請・承認

### UC-X010: 経費精算を申請する

1. 社員が明細一覧 (1件以上) を確認する。対象期間は明細の利用日から自動表示されるだけで、
   ここで編集する項目ではない
2. 明細を追加・修正・削除する
3. 承認者を指定する (固定ルートまたは都度指定、原則5)
4. 申請する。`expense_claims.status` が申請中になる
5. 承認者へ通知する

### UC-X011: 経費精算を承認する (勤怠実績との突合せ表示)

1. 承認者が申請一覧を開く
2. 各明細について、`fact_reference_id` が指す勤怠実績・予定・出張申請の内容を
   並べて表示する (例: 「7/4 客先訪問と記録あり」)
3. 突合せ結果に矛盾があれば差戻す (勤怠側のデータは書き換えない)
4. 問題なければ承認する
5. `expense_categories` の承認ルールにより、しきい値以下の区分は承認を1段階省略できる

### UC-X012: 経費精算のバックオフィス処理

1. 経理担当者が承認済み経費精算を確認する (UC-B004の対象を全経費区分に拡張)
2. 領収書 (添付がある明細のみ)・金額・用途・勘定科目を確認する
3. 不備があれば差戻す
4. 問題なければ支払予定にする
5. 会計CSV(`generic`/`moneyforward`/`freee`から選択)・証跡アーカイブExcel・
   freee/MoneyForwardへの外部API送信のいずれかで出力する
6. 支払後に完了にする

`backoffice_tasks.task_type` は経費精算1種類のままでよく、区分ごとに種別を分けない
(勘定科目のマッピングは区分マスタ側の設定で吸収する)。

手順5の実装は`GET /exports/expenses`(会計CSV)・`GET /exports/expenses.xlsx`
(証跡アーカイブExcel)・`POST /exports/expenses/external-publish`(外部API送信、フェーズ3)の
3エンドポイント。会計CSVは`format`パラメータで`generic`(タスク単位・後方互換)・
`moneyforward`・`freee`(いずれも明細=仕訳1行、`expense_categories.account_code`/`tax_category`
をそのまま使用)を切り替えられる。証跡アーカイブExcelは`ExpenseExcelBuilder`が生成し、
`InternalArchivePublisher`経由でローカルストレージへ内部保存した上で`internal_archive.created`を
stored_eventsへ記録する。

`POST /exports/expenses/external-publish`(freee/MoneyForwardへの実API送信)は`year_month`
(対象月、複数可)・`provider`(`freee`/`moneyforward`)・任意の`employee_id`(複数可)を指定し、
承認済み(`expense_claims.status = approved`)の経費精算のみを対象とする(未承認・差戻し中の
申請は送信対象から除外)。対象月は確定基準の日付(承認日時→提出日時→精算期間開始日の順で
最初に存在するもの)を基準に判定する。勤怠側の外部API連携(フェーズ2、
[docs/33-usecases-attendance-external-api.md](./33-usecases-attendance-external-api.md))と
同じ認可基盤(`ExternalIntegrationConnection`・`AuthStrategy`)と従業員マッピング
(`ExternalEmployeeMapping`。申請者=`employee_id`をそのまま`user_id`として参照し、経費専用
テーブルは追加しない)を再利用する。送信成功時のみ`external_integration.published`を
stored_eventsへ記録し、対象データID(`expense_claims.id`)+連携先+出力種別+実行回数から
導出した冪等性キーで重複送信を検知する(送信失敗した申請は自動リトライせず、手動で再実行する。
実サーバーへの疎通確認は本フェーズでは行わずHttp::fake()でのテストに留める)。

連携先ごとのペイロード構造・送信方式は次のように異なる(一次情報の調査結果、
[docs/notes/moneyforward-api-investigation.md](./notes/moneyforward-api-investigation.md)参照)。

- **freee**: `FreeeExpenseApiPayloadBuilder`が仕訳相当のペイロードを組み立て、通常の
  `ExternalApiPublisher`が`POST /api/1/deals`へ1リクエストで送信する。`expense_categories.account_code`/
  `tax_category`を勘定科目・税区分としてそのまま使う。
- **MoneyForward**: MoneyForwardクラウド経費APIは仕訳を直接受け取らず、**経費明細
  (ex_transaction)を1件ずつ作成する**モデルである。`MoneyForwardExpenseApiPayloadBuilder`が
  経費明細(`ExpenseItem`)1件につきex_transaction 1件分のペイロードを組み立て、
  `MoneyForwardExpensePublisher`(`app/Domain/Export/Services/Publishers/`)が
  `POST /api/external/v1/offices/{office_id}/office_members/{office_member_id}/ex_transactions`
  へ明細ごとに送信する。領収書が添付されている明細は、先に
  `POST .../office_members/{office_member_id}/upload_receipt`で画像をアップロードし、
  その結果(`receipt_input`)をex_transaction作成リクエストへ紐付けてから送信する。
  `ex_item_id`(経費科目id)・`dr_excise_id`(税区分id)はコードではなくMoneyForward内部の
  管理IDのため、`expense_categories.account_code`/`tax_category`をそのまま送らず、
  `external_account_mappings`テーブル(`ExternalAccountMapping`モデル)経由でMoneyForward内部IDへ
  変換する。事前に管理者が`account_code`/`tax_category`とMoneyForward内部IDの対応を
  `external_account_mappings`へ登録しておく必要がある。またURLパスの`office_id`は
  `external_integration_connections.external_office_id`(連携先ごとに1つ)、
  `office_member_id`は`external_employee_mappings.external_employee_code`を流用する。

## 実装上のポイント

- 通勤費・業務交通費・その他経費は `expense_categories` の値が違うだけで、
  データモデル・Command/Event・承認フロー・バックオフィス処理はすべて共通。
- **申請の入り口は「対象期間の指定」ではなく「経費区分の選択」。** `expense_claims`は
  ユーザーが期間を入力して作成するものではなく、明細を1件保存した時点で暗黙に作成される。
  `period_from`/`period_to`は明細の`usage_date`の最小値・最大値から算出する派生値として
  Projector側で保持し、ユーザー入力欄としては公開しない (原則2)。
- `expense_categories.entry_mode` (`batch`/`single`) によって、区分選択直後にどの入力
  フォームを開くかを切り替える。区分が増えても`entry_mode`の値を設定するだけでよく、
  フロントエンド側の分岐ロジックを増やさない。
- 会食・宿泊・消耗品等の`single`区分も、交通費と同じく最終的には`expense_items.description`
  1項目に整形済みテキストを格納する。区分ごとの入力しやすさは**フロントエンドの入力フォームの
  違いだけで実現し、バックエンドのデータ構造は増やさない** (交通費の「出発地 → 到着地
  (交通手段)」と同じパターン)。
- 勤怠実績への参照は「入力補助」「承認時の突合せ表示」に限定し、経費明細の金額計算・
  確定判定には使わない。
- `expense_route_templates` は個人用・全社共有をスコープの違いとして1テーブルで表現し、
  マスタCRUDのみで運用する (Command/Eventの対象にしない)。
- 定期券区間の重複判定は初期段階では自己申告とし、将来の自動判定もCommandHandler側の
  ロジック拡張として吸収し、明細のデータ構造は変えない。
- バックオフィス処理は既存のUC-B004 (経費精算) パターンをそのまま経費区分横断で使う。
