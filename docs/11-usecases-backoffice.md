# 11. バックオフィス処理ユースケース

## UC-B001: バックオフィスタスクを自動作成する

1. 申請が最終承認される
2. 申請種別設定を確認する
3. バックオフィスタスクが必要なら作成する
4. 処理部署、初期ステータス、期限を設定する
5. 担当者候補へ通知する

## UC-B002: 担当者を割り当てる

1. バックオフィス担当者が未担当タスク一覧を開く
2. キーワードでタイトル・種別・担当部署・担当者を検索し、必要に応じてページを移動する
3. 対象タスクを個別または表示ページ単位で一括選択する
4. 担当者を割り当てる
5. ステータスを確認中にする
6. 担当者へ通知する

## UC-B003: 処理ステータスを更新する

1. 担当者が自分のタスクを開く
2. 処理状況を確認する
3. ステータスを更新する
4. コメントを残す
5. 履歴を記録する

自分の担当タスク一覧も検索・ページングに対応し、完了・取消以外のタスクを個別または表示ページ
単位で選択して一括完了できる。一括完了APIは自分に割り当てられたタスクだけを受け付け、1件でも
他人のタスクが含まれる場合は全体をエラーとして扱う。各タスクの完了は通常の
`ChangeBackOfficeTaskStatus`コマンドを通し、個別操作と同じイベント・遷移規則を適用する。

### ステータス例

- 未着手
- 確認中
- 不備あり
- 処理中
- 発注済
- 支払予定
- 発送済
- 完了
- 取消

## UC-B004: (欠番、経費精算は専用ドメインに統合)

経費精算・交通費精算のバックオフィス処理は、汎用申請 (`workflow_requests`) 経由ではなく
経費精算専用ドメインに統合された。処理フローは
[30章 経費精算ユースケース](./30-usecases-expense.md) の UC-X012 を参照。

## UC-B007: 月次勤怠確認タスクを処理する

経費精算(UC-B004参照)と同じく、月次勤怠も汎用申請(`workflow_requests`)経由ではなく
勤怠ドメイン専用の承認フロー([7章 UC-A008〜UC-A010](./07-usecases-attendance.md))を
持つため、バックオフィスタスクの自動作成は`attendance.month_approved`イベントを起点に行う
(UC-B001の`workflow_requests`起点の自動作成とは別経路)。

1. 月次勤怠が承認される(`attendance.month_approved`)
2. 人事部の未担当タスクとしてバックオフィスタスク(`task_type: attendance_month_confirmation`、
   `source_type: attendance_month`)を自動作成する
3. 人事部担当者へ通知する
4. 担当者が対象社員の月次勤怠実績を確認する
5. タスク詳細画面から、対象社員・対象月を固定した給与計算用CSVまたはExcel勤怠管理表を出力する
6. 問題がなければ対象月を締める(`attendance.month_closed`)。締め後は日次勤怠・打刻ログの
   通常編集が一律ロックされ、修正が必要な場合は修正申請ワークフロー([10章](./10-usecases-workflow.md))
   を使う
7. タスクを完了にする

締めはタスク単位(対象社員×対象月)で個別に行う。管理部が対象月を選択して社員全員分を
一括で確認・締める専用画面は持たない(未提出・未承認の検出は月次勤怠一覧・承認待ち一覧側で
行う)。CSV/帳票出力自体は締め前(承認済み時点)でも可能で、締めは「バックオフィス確認が
完了し、以降その月の実績を変更しない」という意思表示として行う。

## UC-B005: 名刺申請を処理する

1. 総務担当者が承認済み名刺申請を確認する
2. 氏名、部署、役職、メール、電話番号を確認する
3. 発注データを作成する
4. 発注済みにする
5. 納品後、発送済みにする
6. 完了通知を送る

## UC-B006: 備品・グッズ申請を処理する

1. 総務担当者が承認済み申請を確認する
2. 在庫を確認する
3. 在庫があれば引当する
4. なければ発注済みにする
5. 発送または手渡し後に完了にする

## UC-B008: 勤怠確定取消依頼を処理する

「勤怠確定取消依頼」(`request_types.code: attendance_confirmation_revert`)は汎用申請
(`workflow_requests`)経由で申請・承認され、承認完了によりUC-B001の自動作成フローで
バックオフィスタスク(`task_type: attendance_confirmation_revert`、人事部担当)が作成される。

1. 申請が承認され、人事部の未担当タスクとしてバックオフィスタスクが自動作成される
2. バックオフィス担当者(人事部担当者)がタスクを確認する
3. 対象年月・取消理由をもとに、対象の月次勤怠(`status = approved`)の確定を取り消す
   ([7章 UC-A018](./07-usecases-attendance.md#uc-a018-承認済みの月次勤怠の確定を取り消す勤怠確定取消依頼)、
   `attendance.month_confirmation_reverted`)
4. タスクを完了にする

確定取消の実行権限はバックオフィス担当者専用で、対象月は`not_submitted`に戻る。以降は
通常の日次編集→再提出→再承認フローに乗る。

## 実装上のポイント

- バックオフィス処理は承認とは別ステータス系列として管理する
  (`workflow_requests.status` と `backoffice_tasks.status` は独立)。
- タスク種別 (`task_type`) ごとに処理フロー・ステータス遷移が異なるため、
  ステータス遷移のバリデーションはタスク種別単位で定義する。
- `source_type` / `source_id` で `workflow_requests` など発生源に紐づく (ポリモーフィック)。
