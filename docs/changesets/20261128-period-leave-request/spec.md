# period-leave-request(段階③b: 期間・複数日の休暇を1つの申請にする)

ステータス: レビュー中

## 変更要望と決定(ユーザーの回答 2026-11-28)
- 期間の休暇の申請は1つの申請として、どれか1日でも拒否されたら全部申請しない。
- 承認が必要な設定でも、1つの申請(ワークフローも1件)にする。
- 申請の日は今の申請の画面の仕様に合わせる: 期間(開始日〜終了日)の指定と、日を個別に選ぶ指定(週次の選択から `?dates=` で来る複数日を含む)の両方。選んだ日に勤務予定の無い日(所定の休日)を含むと拒否する。
- 既存の「期間でまとめて申請された日ごとの申請」(request_group_id の兄弟)は日ごとのまま残す。
- 前提: ③a(`20261128-returned-is-final`)の後に行う(再提出の経路が無くなっているので、日の一覧に対応させなくてよい)。③c(取消の申請)は本変更の後。

## 現状(As-Is)(調査・設計レビュー 2026-11-28)
- 休暇の申請(有給・特別休暇・代休)は1集約=1日(`targetDate` 等)。画面は日ごとに API を呼び、失敗で止まる(前の日だけが申請済み)。期間は暦日をすべて列挙し、複数日は全日に固定。
- 1日=1申請の前提が入っている箇所(設計レビューで確認):
  - 口座: `DesignatePaidLeaveUsageHandler` は「同じ申請 ID の有効な消化があれば既存を返す」(2日目以降が黙って作られない)。Confirm・Cancel は `usageIdForRequest()` で1件だけを引き、対応表は申請 ID→消化 ID で上書きされる。消化 ID は `LeaveUsageId::for(kind, requestId, 再提出回数)`。Reactor は申請の `requestedDays` をそのまま渡す。特別休暇・代休の口座も同じ。
  - 勤怠: `AttendanceDayLeaves::findByRequest` が1行だけを返し、Apply・Recalculate・Release の各 Handler はその行の日を読む(Command の日を使わない)。承認・差戻し・取消の Command は日を持たない。休暇ビューの Projector の状態の遷移も1行だけ。一意のキーは `(leave_kind, leave_request_id)`。
  - 出勤率: `leave_attendance_rate_leaves`・`special_leave_attendance_rate_leaves` の一意のキーが `(leave_kind, leave_request_id)`、`AbstractLeaveAttendanceRateProjector` も1行の前提(他の文脈の表を読まないと明記)。
  - 取得日数: `LeaveUsageQuery` は申請の行の `target_date` で `requested_days` を合計。
  - `target_date` の利用: 一覧の絞り込み・並べ替え(`PaidLeaveController.php:668-675`、勤怠の日の画面が使う)、`WorkflowRequestController.php:306-436`(subject・`requestGroupDates`)、`WorkflowRequestResource.php:65-86`、承認・申請の一覧の要約(`ApprovalsPage.tsx:75-84`、`WorkflowRequestListPage.tsx:149-158`)、mcp の `GetMyLeaveRequestsTool`。
  - 勤務予定の無い日の拒否は既に勤怠の文脈にある(`LeaveApplicabilityPolicy.php:28-33`。文言に日付が無い)。
  - 旧イベントに必須の引数を足すと復元できない(`EventRestorabilityChecker`。既定値付きなら復元できる)。

## 設計前提の検証
- 正データと派生データ: 休暇の申請の正は休暇の文脈の集約、消化は口座、休暇ビューは勤怠、出勤率は休暇の文脈の派生。各文脈が自分の日ごとの行を持つ(他の文脈の表を読まない。原則15)。
- イベントの意味: 申請のイベントは「この日の一覧の休暇を申請した」という1つの事実。
- data-correction: 旧イベントの読み替えではなく、イベントの形をそろえる方を先に考える(論点5)。

## 仕様検討

### 論点1: 申請の形
- 決定:
  - 休暇の申請の集約が日の一覧(`dates`、並べ替えて正規化)を持つ。1日の申請は日が1つ。集約は重複した日・2日以上で全日でない単位を拒否する。
  - 単位: 2日以上は全日だけ。1日は全日・半日・時間(今と同じ)。申請の日数は日の数(1日の半日・時間は今の換算)。
  - 勤務予定の無い日の判定は、勤怠の文脈の今の判定(`LeaveApplicabilityPolicy`)を使い、文言に日付を加える(「{日付}は勤務予定日ではないため申請できません。」)。休暇の文脈に同じ判定を重ねない。どれか1日でも拒否(衝突・勤務予定なし・締め)なら全体を拒否(連鎖が1つのトランザクションなので全体が戻る)。
- 未確定・要確認事項: なし

### 論点2: 各文脈の日ごとの対応(設計レビュー H1〜H3)
- 決定:
  - 口座(3種): 消化の対応表を(申請 ID, 日)→消化 ID にする。新しい消化 ID は `{kind}:{requestId}:{date}`(旧式の `{kind}:{requestId}:{n}` と衝突しない)。冪等の判定は(申請 ID, 日)。Confirm・Cancel はその申請の有効な消化をすべてたどる。1日の消化は全日なら1.0、1日の申請の半日・時間は今の換算。旧ストリームは消化の指定のイベントの `usedOn` から(申請 ID, 日)を復元する。
  - 勤怠: Reactor は日ごとに Command を出し、その日を渡す。Handler は(kind, 申請 ID, 日)で行を引く。休暇ビューの一意のキーを `(leave_kind, leave_request_id, work_date)` にし、状態の遷移はその申請のすべての行を更新する。特別休暇・代休の Reactor も同じ。
  - 出勤率: イベントから作るまま、自分のテーブル(`leave_attendance_rate_leaves`・`special_leave_attendance_rate_leaves`)の一意のキーに `work_date` を加える。
  - 取得日数: `LeaveUsageQuery` は休暇の文脈の日の子テーブル(`*_request_days`)から合計する。
  - 申請の行の `target_date` は開始日(日の一覧の最初の日)とし、日付での絞り込みは日の子テーブルで行う。一覧・承認・ワークフローの要約・mcp の応答は日の一覧(`dates`)と日数を含める(`target_date` は互換のため残す)。
  - ワークフロー: 1件。下書きの `formData` に日の一覧。承認の詳細に期間・日の一覧・日数。`RequestGroupNotice` は既存の兄弟の申請の承認の画面だけ。
- 未確定・要確認事項: なし

### 論点3: 入口と画面
- 決定:
  - 直接の申請・ワークフローの申請は本文に `dates`(1日以上)を受け、1つの Command を dispatch する。デプロイの合間の互換のため、当面は `target_date` も受け、`dates:[target_date]` として扱う。新しい申請の `request_group_id` は無視する(兄弟の申請は作らない)。
  - 画面: 期間・個別の日の指定のどちらも、選んだ日を一覧で出し、勤務予定の無い日はその場で示して送れなくする(勤務予定は既存の勤怠の予定の API で取る。実装の最初に確かめる)。送信は1回。
- 未確定・要確認事項: なし

### 論点4: 取消(③c の前の状態)
- 決定: 申請中の申請は申請全体を取り下げる(ワークフローの取消)。承認済みの休暇の取消は、③c までは今と同じく直接(申請の単位=日の一覧全体)。勤怠の日の画面の取消も申請の単位で、確認の文に期間を出す。
- 未確定・要確認事項: なし

### 論点5: 旧イベントの扱い
- 決定: イベントに `dates`(既定値 `[]`)と `targetDate`(既定値 null)の両方を持たせ、`days()` で日の一覧を返す(旧イベントは `[targetDate]`)。3種の各 Reactor・Projector は `days()` だけを使う。`stored_events` の書き換え(移行)はしない(旧イベントは1日の申請のまま正しく、ユーザーの判断で既存の申請は日ごとのまま残すため。data-correction の「読み替えをコードに持たない」に対しては、既定値付きの項目の追加(互換の追加)として扱う)。
- 未確定・要確認事項: なし
