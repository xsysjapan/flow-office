# period-leave-request(段階③: 期間の休暇を1つの申請に。差戻しは最終の結果、承認済みの休暇の取消は承認の設定に従う)

ステータス: 検討中

## 変更要望(原文)と決定(ユーザーの回答 2026-11-28)
> まとめて保存系の一括操作についてもAPIを用意して処理してください。(段階③: 期間の申請)
- 期間の休暇の申請は1つの申請として、どれか1日でも拒否されたら全部申請しない。
- 承認が必要な設定でも、期間で1つの申請(ワークフローも1件)にする。
- 期間に所定の休日(勤務予定の無い日)を含むと拒否する。
- 既存の「期間でまとめて申請された日ごとの申請」(request_group_id の兄弟)は日ごとのまま残す。
- 申請は出した単位で取り消す。申請の修正はできない。
- 差戻しは申請(ワークフロー)の最終の結果。再申請は新しいワークフローを始める(今の「同じ申請を提出し直す」をやめる)。
- 承認済みの休暇の取消は、休暇の種類の承認の設定に従う: 承認不要なら直接取り消す。承認が必要なら取消の申請を出す(休暇申請の承認の取消ではない。原則13)。
- 既存の実装と矛盾する場合は、移行を検討して相談する。

## 背景・目的
- 今は1日=1申請で、期間の申請は画面が日ごとに API を呼ぶ(途中で失敗すると前の日だけが申請済みになる)。承認が必要な設定では日数分のワークフローができる。
- 申請(ワークフロー)と業務(休暇)の分担をはっきりさせる(原則14): 申請は承認・差戻しで終わる。承認後に残るのは業務の休暇で、その取消は業務の操作(承認の設定に応じて取消の申請を経る)。

## 現状(As-Is)(調査 2026-11-28、investigator)
- 休暇の申請(有給 `PaidLeaveRequestAggregate`・特別休暇・代休)は1集約=1日(`targetDate`・`leaveType`・`hours`・`requestedDays`・`requestGroupId`)。Projector は申請の行を1行(`paid_leave_requests` 等)。
- 1日=1申請の前提が入っている箇所:
  - 口座の消化(`PaidLeaveUsageOnPaidLeaveRequestReactor` 等): 申請ごとに `usedOn` 1日の消化の記録。取消は `usageIdForRequest(申請ID)`。
  - 勤怠の休暇ビュー(`AttendanceDayLeaveProjector`): `(leave_kind, leave_request_id)` で一意。勤怠の反映(`ApplyLeaveToAttendanceDay`・`ReleaseLeaveFromAttendanceDay`・`LeaveDayConflictPolicy`)は日ごと。
  - ワークフロー: 下書きの `formData` は1日分。`LeaveRequestWorkflowLinks` は1ワークフロー=1申請。兄弟の承認(`PaidLeaveApprovalOnWorkflowRequestReactor`)は request_group_id で兄弟を探して承認する。
  - 出勤率の集計(`AbstractLeaveAttendanceRateProjector`)・過去1年の取得日数(`LeaveUsageQuery`)は行ごと。Excel は休暇ビューの日ごとの行。
  - 画面: 期間は暦日をすべて列挙し、複数日は全日に固定(`MyPaidLeavePage.tsx:48-57,89-90`)、日ごとに送信し失敗で止まる(:132-160)。承認の詳細に「期間で N 日分まとめて申請、1件を承認すると残りも承認」(`RequestGroupNotice`)。
- 差戻し: ワークフローは申請前の状態に戻り、申請者が「提出する」で同じ申請を提出し直す(docs/10 UC-W004、docs/09「差戻し・再申請・取消」)。休暇は申請前(差戻し)に戻り、再提出で申請中に戻る(`Resubmit{X}`)。
- 取消: 申請者・管理者が申請中・差戻し・承認済みの休暇を直接取り消せる(承認済みは残数を戻す。承認済みのワークフローは取り消さない)。各休暇の画面の取消は申請中・差戻しだけ、勤怠の日の画面は申請中・承認済み(変更セット`20261127-attendance-day-leave-separate-actions`)。
- 承認の要否は休暇の種類ごとの全体の設定で、入口は直接の申請(`/requests`)とワークフローの申請(`/requests/workflow`)に分かれている(変更セット`20261128-single-command-entrypoints`)。

## 設計前提の検証
- 正データと派生データ: 休暇の申請(業務)の正は休暇の文脈の集約、ワークフローの正はワークフローの文脈、消化は口座の文脈、休暇ビューは勤怠の文脈の派生。期間の申請でも、各文脈の正の置き場所は変えない。
- イベントの意味: 期間の申請のイベントは「この期間(日の一覧)の休暇を申請した」という1つの事実。消化・勤怠は日ごとの事実として各文脈が記録する。
- 原則13: 差戻しを最終にしても、承認・差戻しのイベントは書き換えない。承認済みの休暇の取消は新しい状態遷移(取消の申請→承認→休暇の取消)。
- 原則14: 取消の申請はワークフローの申請の1種類(業務の対象は既存の休暇の申請)で、取消の業務の処理は休暇の文脈に置く。
- 横展開: 差戻しを最終にする規則はワークフロー全体(月次勤怠・経費・振替休日・備品の貸出・汎用の申請種別)に関わる(論点5)。

## 仕様検討

### 論点1: 期間の申請の形
- 決定:
  - 休暇の申請(有給・特別休暇・代休)の集約が日の一覧(`dates`)を持つ。1日の申請は日が1つの期間の申請(同じ形)。
  - 単位: 複数日は全日だけ(今の画面と同じ)。1日のときは全日・半日・時間を選べる(今と同じ)。
  - 申請のイベントは日の一覧を持つ(新しい版のイベント。旧イベントの `targetDate` は日が1つの一覧として読む)。
  - 申請の日数は日の数(全日)。1日の半日・時間は今と同じ換算。
  - 期間に勤務予定の無い日を含むと拒否(422「{日付}は勤務予定日ではないため申請できません。」)。期間の日の重複・他の休暇との衝突・締めの判定は、全部の日について確かめ、どれか1日でも拒否なら全体を拒否する。
- 未確定・要確認事項: なし

### 論点2: 各文脈の連鎖
- 決定:
  - 口座(消化): 申請の日ごとに消化の記録を作る(消化の記録の ID は申請 ID と日から決まる)。申請の取消・休暇の取消で、その申請のすべての日の消化を取り消す。
  - 勤怠(休暇ビュー): 申請の日ごとに休暇ビューの行を作る。一意のキーを `(leave_kind, leave_request_id, work_date)` にする。勤怠の反映・解除は日ごと(今の処理を日の一覧に広げる)。
  - ワークフロー: 期間で1件。下書きの `formData` に日の一覧を持つ。`LeaveRequestWorkflowLinks` は今どおり1ワークフロー=1申請。
  - 出勤率の集計・過去1年の取得日数・Excel・CSV: 日ごとの行(休暇ビュー・消化)から作る形にそろえ、申請の行の数に依存しないようにする。
  - 承認の詳細の画面: 期間(日の一覧と日数)を出す。`RequestGroupNotice` は既存の兄弟の申請のためだけに残す。
- 未確定・要確認事項: なし

### 論点3: 入口と画面
- 決定:
  - 直接の申請(`POST /{kind}/requests`)とワークフローの申請(`/requests/workflow`)は、本文に `dates`(1日以上)を受ける。1回の呼び出しで1つの Command(原則17)。
  - 画面: 期間・日付を選ぶと、勤務予定の無い日があればその場で示して送信できなくする(勤務予定は既存の勤怠の予定の API で取る。実装の最初に確かめる)。送信は1回。
  - `request_group_id` は新しい申請では使わない(期間が1つの申請のため)。既存の兄弟の申請と兄弟の承認の Reactor は残す。
- 未確定・要確認事項: なし

### 論点4: 取消
- 決定:
  - 申請中の申請: 申請者は申請全体を取り下げられる(ワークフローの取消。今と同じく、休暇の申請も取り消される)。
  - 承認済みの休暇(承認が必要な設定で承認された休暇、承認不要で直接作った休暇): 取消は申請の単位(期間全体)。
    - 休暇の種類が承認不要の設定: 申請者が直接取り消す(今と同じ。残数が戻る)。
    - 承認が必要な設定: 申請者は「取消の申請」を出す。取消の申請はワークフローの申請の1種類(業務の対象は既存の休暇の申請)。取消の申請が承認されると、休暇の文脈が休暇を取り消す(残数が戻る・勤怠の休暇ビューから外れる)。差し戻されると休暇はそのまま。取消の申請中は、同じ休暇に2つ目の取消の申請を出せない。
    - 管理者の取消(`admin-cancel`)は今と同じく直接(取消の申請を経ない)。
  - 締めの後(月次勤怠の提出以降)の休暇の取消は、今と同じく申請者にはさせない(原則13。管理者の取消は今の規則のまま)。
  - 取消の置き場所(変更セット`20261128-remaining-entrypoints`の論点7から移した): 各休暇の画面の申請一覧と、勤怠の日の画面の「この日の操作」の両方で、取消(または取消の申請)を出す。勤怠の日の画面からの取消も申請の単位(期間全体)で、確認の文に期間を出す(「{期間}の有給休暇を取り消しますか?」)。
- 未確定・要確認事項: なし

### 論点5: 差戻しは最終の結果(ワークフロー全体)
- 決定:
  - 差戻しをワークフローの終わりの状態にする(承認・却下・取消と同じく、その後の提出はできない)。「提出する」で同じ申請を提出し直す操作をやめる。
  - 再申請は新しいワークフローの申請。申請の画面に「申請し直す」を置き、元の申請の内容を入れた新しい申請の画面を開く。新しい申請は元の申請への参照(`resubmission_of`)を持ち、承認者は前回の差戻しの理由を見られる。
  - 業務側: 差戻しで業務の申請も終わる(休暇の申請は差戻しで終わり、消化は取り消す。今の `Resubmit{X}` の経路は使わない)。月次勤怠・経費は、差戻しで業務の対象が編集できる状態に戻り(今と同じ)、提出し直すと新しいワークフローが始まる。実装の最初に、月次勤怠・経費・振替休日・備品の貸出・汎用の申請種別の今の再提出の経路を確かめ、新しいワークフローを始める形に寄せる。寄せられない(業務の正データの作り直しが要る)ものが見つかれば、ユーザーに相談する。
- 既存のデータ:
  - 過去に「差戻し→同じワークフローで再提出」された履歴は、そのまま残す(イベントは書き換えない。Projector は過去の再提出のイベントを今どおり読めるようにする)。
  - 今差戻し中のワークフローは、差戻しで終わった申請として扱う(申請者は「申請し直す」で新しい申請を出す)。データの移行はしない。差戻し中の休暇の申請も同じく終わった申請として扱う。
  - 上の扱いで既存のデータと矛盾が出る(例: 差戻し中のワークフローに業務側が「申請前」の状態を前提にした処理が残る)場合は、実装を止めてユーザーに相談する。
- 未確定・要確認事項: なし(矛盾が見つかった場合のみ相談)

### 論点6: 既存の日ごとの申請
- 決定: 既存の申請(1日=1申請・兄弟の申請)はデータを移行せずに残す。新しい形の集約は、旧イベント(`targetDate`)を日が1つの期間として読む。兄弟の承認の Reactor は既存の兄弟のために残す。
- 未確定・要確認事項: なし

(設計レビューの後に、実装者向けに確定する。下は現時点の案)
- backend:
  - 休暇の申請の集約・イベント(新しい版)・Projector(申請の行と日の子テーブル `*_request_days`)。旧イベントの読み替え。
  - 口座の消化・勤怠の休暇ビュー・ワークフローの下書き・出勤率・取得日数・Excel・CSV の日の一覧への対応(論点2)。
  - 入口の本文の `dates`(論点3)。
  - 取消の申請(ワークフローの種類、休暇の文脈の取消の処理、承認の設定による入口の分岐は段階①と同じく呼び出し側が選び、Handler が設定に応じて拒否する)(論点4)。
  - 差戻しを終わりの状態にし、再申請を新しいワークフローにする(論点5)。
- frontend: 休暇の3画面(期間の1回の送信、勤務予定の無い日の表示、取消と取消の申請)、勤怠の日の画面の取消、申請の詳細の「申請し直す」、承認の詳細の期間の表示。
- テスト(`domain-test`、業務シナリオのテスト):
  - 期間の申請: 承認不要で期間の全日の休暇・消化・休暇ビューができる/1日の衝突・勤務予定の無い日・締めで全体が拒否され何も残らない/承認が必要で1件のワークフロー→承認で全日が承認。
  - 取消: 申請中の取下げ、承認不要の承認済みの直接の取消、承認が必要な承認済みの取消の申請→承認で休暇の取消・残数が戻る、取消の申請の差戻しで休暇がそのまま、締めの後は申請者が取り消せない。
  - 差戻し: 差戻しでワークフロー・休暇の申請が終わり提出できない、「申請し直す」で新しいワークフロー(元への参照)、月次勤怠・経費の差戻し→提出し直しで新しいワークフロー。
  - 既存のデータ: 旧イベントの申請・兄弟の申請・過去の差戻し→再提出の履歴が作り直しで今と同じ状態になる。
  - 作り直し: 代表のシナリオの後に ReadModel を作り直して同じ状態。

## 受け入れ条件
- 期間の休暇が1回の操作・1つの申請(ワークフローも1件)で申請され、どれか1日でも拒否されると何も残らない。勤務予定の無い日を含むと申請できない。
- 申請中は申請全体を取り下げられる。承認済みの休暇は、承認不要なら直接、承認が必要なら取消の申請で、申請の単位で取り消せる。
- 差戻しは申請の最終の結果で、再申請は新しいワークフローになる(全種類)。
- 既存の日ごとの申請・兄弟の申請・過去の履歴が今と同じに動き、作り直しで同じ状態になる。
- 上のテストと全件の単体テスト、変えた画面を通る E2E の spec が通る。
