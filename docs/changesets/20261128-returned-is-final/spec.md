# returned-is-final(段階③a: 差戻しを申請の最終の結果にし、再申請は新しいワークフローにする)

ステータス: レビュー中

## 変更要望と決定(ユーザーの回答 2026-11-28)
- 申請は出した単位で取り消す。申請の修正はできない。
- 差戻しは申請(ワークフロー)の最終の結果。再申請は新しいワークフローを始める。
- 備品の貸出の申請: 差戻しで貸出の申請も終える。既存の差し戻された行は補正しない。
- 既存の実装と矛盾する場合は、移行を検討して相談する。
- 段階③(期間の申請)の設計レビューの勧めで、③a 差戻しの最終化 → ③b 期間の申請(`20261128-period-leave-request`)→ ③c 取消の申請(`20261128-leave-cancellation-request`)の順に分けた(③a を先にすると、③b で再提出の経路を日の一覧に対応させる作業が要らなくなる)。

## 現状(As-Is)(調査・設計レビュー 2026-11-28)
- docs/10 UC-W004: 差し戻されたワークフローは申請前の状態(差戻しのメッセージ付き)に戻り、申請者が「提出する」で同じ申請を提出し直す。docs/09「差戻し・再申請・取消」: 休暇は差戻しで申請前に戻り、再提出(`Resubmit{X}`)で申請中に戻る。
- 同じワークフローを提出し直す経路を使うのは、休暇3種(Resubmit の Reactor)と、汎用の申請種別・備品の貸出(`SubmitWorkflowRequestHandler.php:43` が差戻しからの提出を許す)。月次勤怠・経費は今も提出のたびに新しいワークフローを作り(業務側は差戻しの状態から提出を受ける)、振替休日は業務側の差戻しが既に終わり。
- 申請の画面の「提出する」は差戻しのどの種類にも出る(`WorkflowRequestDetailPage.tsx:218`)。月次勤怠・経費・振替休日では、業務側の再提出なしにワークフローだけが申請中に戻りうる(既存のデータに不整合があるかもしれない)。
- 差戻しの後の取消: `WorkflowRequestStatus::cancellable()` に差戻し(`:35`)、画面(`statusLabels.ts:100`、`WorkflowRequestDetailPage.tsx:232`)、休暇の集約の取消(`PaidLeaveRequestAggregate.php:149-152` ほか)、休暇の画面の取消のボタン(`MyPaidLeavePage.tsx:325` ほか)が差戻しからの取消を許す。古い差戻し済みの月次勤怠のワークフローを取り消すと、`AttendanceMonthCancelOnWorkflowRequestCancelledReactor` が、新しいワークフローで提出済みの月も未提出に戻してしまう(どのワークフローかを照合していない。推測)。
- 備品の貸出の申請: `AssetLoanRequestOnWorkflowRequestReactor` に差戻しの処理が無く、差戻しの後も承認待ちのまま(今は差戻し中のワークフローを取り消すと取り下げになる)。差戻しを終わりにすると承認待ちのまま残り、`AssetActiveBusinessGuard` がその備品の削除・管理区分の変更を拒否し続ける。`asset_loan_requests` は Reactor が書いている(Projector ではない)ので作り直しの対象外。
- ホームのダッシュボード(`HomeDashboardPage.tsx:13`)は差戻しを「対応待ち」に数える。
- docs/10 UC-W003-2 は、差戻しと却下を「再提出できるか」で区別している。

## 設計前提の検証
- 原則13: 承認・差戻しのイベントは書き換えない。差戻しを終わりにするのは、今後の状態遷移の規則の変更。
- 原則14: 再申請は新しいワークフロー。業務側(月次勤怠・経費)は、差戻しで業務の対象が編集できる状態に戻る(今と同じ)。
- 原則2: 過去の「差戻し→同じワークフローで再提出」のイベントは残し、Projector と集約は今どおり読めるようにする(Resubmitted の apply・Projector の handler・`LeaveUsageId` の回数の意味を残す)。

## 仕様検討

### 論点1: ワークフローの状態遷移
- 決定:
  - 差戻しを終わりの状態にする(承認・却下・取消と同じ)。差戻しのワークフローは提出も取消もできない(`SubmitWorkflowRequestHandler` の差戻しからの提出を拒否、`cancellable()` から差戻しを外す)。
  - 差戻しと却下の違い(docs/10 に書く): 差戻しは「申請し直す」を出せ、業務側は編集できる状態に戻る(月次勤怠・経費)か終わる(休暇・振替休日・備品の貸出)。却下は申請し直さない(業務側を持つ申請は却下できない。今と同じ)。
- 未確定・要確認事項: なし

### 論点2: 業務側の差戻し
- 決定:
  - 休暇3種: 差戻しで休暇の申請も終わる(差戻し=終わり。消化は今と同じく取り消す)。差戻しの休暇は取り消せない(集約の取消から差戻しを外す)。Resubmit の経路(Reactor・Command)は新しい提出では使わない。旧イベントは読めるように残す。
  - 備品の貸出の申請: 差戻しのイベントを受けて、貸出の申請を「差戻し(終わり)」にする Reactor の処理を足す(ユーザーの判断。既存の差し戻された行は補正しない)。
  - 汎用の申請種別: 差戻しで終わり。
  - 月次勤怠・経費・振替休日: 業務側は今と同じ(月次勤怠・経費は差戻しで編集できる状態に戻り、提出し直すと新しいワークフロー。振替休日は差戻しで終わり)。
- 未確定・要確認事項: なし

### 論点3: 「申請し直す」
- 決定:
  - 新しいワークフローは元の申請への参照(`resubmissionOf`)を持つ。`WorkflowRequestDrafted` の payload に任意の項目(最後の引数・既定値 null)として足す(作り直しで再現するため)。検証: 同じ申請者、元が差戻し、同じ種類。
  - 新しい申請の応答に、元の申請の差戻しの理由(コメント・差し戻した人・日時)を含める(元と違う承認者は元の申請を開けないため)。
  - 種類ごとの動き:
    | 種類 | 「申請し直す」 |
    |---|---|
    | 休暇3種 | 休暇の画面を、元の内容(日・単位・時間・理由・承認者)を入れて開く。送ると新しい休暇の申請とワークフロー |
    | 月次勤怠・経費 | 業務の画面へ移る。業務の画面から提出し直すと新しいワークフロー(業務側の提出の API が `resubmission_of` を受ける) |
    | 振替休日 | 振替の申請の画面を、元の内容を入れて開く |
    | 汎用の申請種別・備品の貸出 | 元の内容(フォームの値・添付)を複製した新しい下書きを作る。添付は複製する(添付が必須の判定に通るように) |
  - 申請の画面の「提出する」は、下書きにだけ出す(差戻しには出さない)。
- 未確定・要確認事項: なし

### 論点4: 既存のデータ
- 決定:
  - 今差戻し中のワークフローと業務(休暇・汎用・備品の貸出)は、差戻しで終わった申請として扱う。移行はしない(備品の貸出の既存の行は補正しない: ユーザーの判断)。
  - 実装の前に、`stored_events` で「差戻しの後に提出」が続いたワークフローを種類ごとに数える(月次勤怠・経費・振替休日でワークフローだけが申請中に戻った不整合があるか)。不整合が見つかれば、実装を止めてユーザーに相談する。
  - ホームのダッシュボードの「対応待ち」から差戻しを外す。
- 未確定・要確認事項: なし(不整合が見つかった場合のみ相談)

## 仕様確定事項(まとめ)
- backend: 論点1・2のワークフローと業務側の状態遷移、論点3の `resubmissionOf`(イベントの項目・検証・応答の差戻しの理由)、業務側の提出の API(月次勤怠・経費)の `resubmission_of`。
- frontend: 申請の画面(差戻しで「申請し直す」、「提出する」は下書きだけ、差戻しで取消を出さない)、休暇・振替休日の画面の元の内容の入力、休暇の画面の差戻しの取消のボタンを外す、ホームの対応待ち。
- テスト(業務シナリオのテスト): 種類ごとに 差戻しで提出・取消ができない/「申請し直す」で新しいワークフロー(元への参照・差戻しの理由)/業務側の状態(休暇は終わり・消化は取消、月次勤怠・経費は編集できる、備品の貸出は差戻し)/古い差戻し済みの月次勤怠のワークフローを取り消せない(月を巻き戻さない)/過去の「差戻し→再提出」の履歴が作り直しで今と同じ状態。

## 受け入れ条件
- 差戻しはどの種類でもワークフローの最終の結果で、提出・取消ができない。再申請は「申請し直す」からの新しいワークフローになる。
- 備品の貸出の申請は差戻しで終わり、備品の削除・管理区分の変更を妨げない。
- 過去の履歴は作り直しで同じ状態になる。
- 上のテストと全件の単体テスト、変えた画面を通る E2E の spec が通る。

- 既存の差し戻された備品の貸出の申請の補正
