## 背景・目的
入力した内容が消える、または失敗が画面に出ないため、利用者が何が起きたか分からない。

## 現状(As-Is)(調査 2026-11-27、investigator。コードの読みによる)

### 1. 経費の申請: 下書きの無い状態の初回の保存で、入力が消える
- `pages/expense/ExpenseClaimNewPage.tsx`:
  - 保存は `ensureClaimId()`(:552-557)で下書きを作り(`createClaim`)、`setClaimId` してから明細を追加する(`addItem`)。
  - `claimId` が付くと `useExpenseClaim(claimId)` の取得が始まり(作成の応答で詳細のキャッシュは作られない)、`if (claimId && isLoadingClaim) return <LoadingState />`(:675)で入力の部分が全部アンマウントされる。
  - そのため、初回の保存では成功・失敗に関わらず入力の部品が1回作り直される。
- 影響:
  - 単票入力(`SingleExpenseItemForm`、値は部品の内部の state)は、明細の追加が 422 になると入力が消え、項目のエラーだけが残る。
  - 表形式(`ExpenseItemsTable`)の行の値はページの state なので残るが、部品の内部の state(選択の行、貼り付け欄、一括の日付・摘要、出発地・到着地の入力 `routeParts`)は消える。`routeParts` が消えて摘要と食い違う恐れがある。
  - まとめて登録のタイトル(`BulkTitleStep`)は `!claimId` で表示しているため、下書きの作成でアンマウントされる。
- ルート(`/expenses/new`)と key(`id ?? 'new'`)は変わらない。原因は読み込み中の表示の条件だけ。

### 2. 備品の詳細: Dialog の入力の検証のエラーが出ない
- `components/ConfirmActionDialog/ConfirmActionDialog.tsx:77-87` は `onConfirm` の例外を握りつぶし(mutation のエラーは `error` prop で出す前提)、Dialog は閉じない。
- `pages/asset/AssetDetailPage.tsx` の4か所が `onConfirm` の中で検証の `Error` を投げるだけで、画面に何も出ず「押しても何も起きない」状態になる:
  - :114 借用者の未選択、:115 承認済みの貸出申請の未選択(貸与)
  - :207 承認者の未選択(貸出の申請)
  - :318 場所の空入力(場所の設定・設置。`confirmDisabled` が無く押せる)
- 同じく `onConfirm` で投げる他の箇所(勤怠の日の削除理由、申請の取消・却下理由、経費の取消理由)は、投げる前に項目のエラーの state を入れて項目の下に出している(変更セット`20261126-field-errors-near-fields`)。

### 3. 働き方の設定: 勤務予定の自動生成の失敗が見えない
- `pages/workCalendar/WorkStylesPage.tsx` の月次の働き方:
  - 保存(`handleSave` :393-412)は、割当(`assignForMonth`)の成功の中で、自動生成(`generateShifts`)を待たずに呼び、続けて確認の表示を閉じる(`setIsConfirming(false)` :407)。
  - 生成の失敗のうち、項目のキーのあるもの(user_id・work_style_id・year_month・from・to)は確認の表示の外の項目の下に出るが、キーの無いもの(`rest`)は確認の表示の中(:499)に描くので、閉じた後は見えない。
  - 生成のエラーは次の操作でも消されず、次に確認の表示を開くと古いエラーが出る見込み(未確認)。
- 割当の失敗は確認の表示が開いたままなので見える。

## 設計前提の検証
- 正データと派生データ: 画面の表示と入力の保持だけ。API・イベントは変えない。
- 原因の分類: 3件とも実装のミス(表示の条件・例外の扱い・表示の位置)。設計の誤りではない。
- 横展開:
  - 1: 同じ「読み込み中で入力を外す」作りの作成画面が他にあるかを実装時に grep で確かめる(`claimId`/`id` を作成の後に state で付けて同じ画面に留まる作り)。
  - 2: `onConfirm` で検証の Error を投げて state を入れない箇所は、frontend 全体で備品の詳細の4か所だけ(調査済み)。
  - 3: 保存の成功の中で別の mutation を待たずに呼び、表示を閉じる作りが他にあるかを実装時に grep で確かめる。

## 仕様検討

### 論点1: 経費の申請の入力の保持
- 選択肢:
  - A. 読み込み中の表示の条件を変える: 画面を開いたときに既存の下書きを読み込む場合(`/expenses/:id/edit` の初回)だけ全体を読み込み中にし、この画面で下書きを作った後の読み込みでは入力の部分を描いたまま、保存済みの明細・提出の部分だけを読み込み中にする。
  - B. 作成の応答で詳細のキャッシュを作り、読み込み中にならないようにする。
  - C. 単票入力の値をページの state へ持ち上げる。
- 決定: A。
- 理由: 原因(作成の後に入力の部分が外れる)を直接直し、単票・表形式・まとめて登録のタイトルのすべてに効く。B は作成の応答が詳細の形と同じかが未確認で、違えば表示の不整合を生む。C は単票にしか効かない。
- 下書きの作成が成功して明細の追加が 422 になったとき、空の下書きがサーバーに残る(今と同じ)。画面は作成済みの下書きの編集として続けられるので、そのままにする(下書き一覧から削除できる)。
- 未確定・要確認事項: なし

### 論点2: 備品の詳細の Dialog の検証
- 選択肢:
  - A. `ConfirmActionDialog` が `onConfirm` の検証の例外を受けて表示する仕組みを足す(検証用の例外の型と mutation の失敗を区別する)。
  - B. 他の箇所と同じ形にする: 投げる前に項目のエラーの state を入れ、その項目の `FormField` の `error` に出す(送信を押した後に出し、入力すると消す)。
  - C. 確定のボタンを `confirmDisabled` で押せなくする。
- 決定: B。
- 理由: 既に4画面で使っている形と揃い、§2.19(エラーは項目の近く)に合う。A は共有の部品の作りを変え、全 Dialog に影響する。C は何が足りないかの文が出ない。
- 再発の防止: `ui-interaction-patterns` §2.19 に「`ConfirmActionDialog` の `onConfirm` で検証の Error を投げるだけにしない(握りつぶされる)。項目のエラーの state を入れてから止める」を1行足す。
- 未確定・要確認事項: なし

### 論点3: 働き方の自動生成の失敗の表示
- 選択肢:
  - A. 生成の失敗(項目に出ないもの)を、確認の表示の外(月次の働き方の欄の、保存のボタンの位置)に `ErrorMessage` で出す。次の保存・入力の変更で生成のエラーを消す(`generateShifts.reset()`)。
  - B. 割当→生成を順に待ち、生成が失敗したら確認の表示を開いたままにする。
  - C. 失敗をトーストで通知する。
- 決定: A。
- 理由: 割当は既に保存されているので、確認の表示を開いたままにする(B)と「保存できていない」と誤解させ、再実行で割当をもう一度送る(冪等か未確認)。A は失敗を確実に見せ、割当が保存済みであることと矛盾しない。トースト(C)は消えるので失敗の表示に向かない(§2.12 は失敗を操作の直近の `ErrorMessage` で返す)。
- 文言: `ErrorMessage` の上に「働き方は保存しましたが、勤務予定の自動生成に失敗しました。」を出す(既存の `ErrorMessage` の `fallback` 等の仕組みに合わせる。仕組みが無ければ `<p>` を添える)。
- 未確定・要確認事項: なし

## 仕様確定事項(まとめ)
1. `ExpenseClaimNewPage`:
   - 全体の読み込み中は「既存の下書きを開いたときの初回の読み込み」だけにする(この画面で作成した下書きの読み込みでは出さない)。判定は、ルートの `id` があり、かつ下書きのデータがまだ一度も読めていないとき。
   - この画面で作成した後の読み込み中は、保存済みの明細・提出の部分だけを読み込み中にし、入力の部分(単票・表形式・まとめて登録のタイトルを含む)はアンマウントしない。
   - `BulkTitleStep` は下書きの作成でアンマウントされないよう、表示の条件を「タイトルの手順が終わったか」の state にする(`!claimId` に依存しない)。
   - 離脱警告(`useUnsavedChangesGuard`・`navigateAfterSave`)と項目エラー(`fieldErrors`)は壊さない。
2. `AssetDetailPage` の4か所: 投げる前に `xxxError` の state を入れ、その項目の `FormField` の `error` に出す(送信の後に出し、値を変えたら消す)。場所の空入力は `LocationTextDialog` の場所の欄に出す。
3. `WorkStylesPage`: 生成の失敗の `rest` を確認の表示の外(保存のボタンの位置)に、文「働き方は保存しましたが、勤務予定の自動生成に失敗しました。」とともに出す。保存の開始・年月・社員・働き方の変更で `generateShifts.reset()` する。
4. 横展開の grep(1・3)で同じ作りが見つかれば、実装結果に記録し、同じ直し方を当てる(見つからなければ「無し」と記録)。
5. スキル: `ui-interaction-patterns` §2.19 に論点2の1行。

## 受け入れ条件
- 経費の申請で、下書きの無い状態から単票を保存して 422 になっても、入力が残り、項目の下にエラーが出る。表形式の出発地・到着地の入力、まとめて登録のタイトルも、初回の保存で消えない。
- 備品の詳細の貸与・貸出の申請・場所の Dialog で、未選択・未入力のまま確定すると、その項目の下にエラーが出る。
- 働き方の設定で、割当が成功し自動生成が失敗すると、確認の表示を閉じた後も失敗の文とエラーが見える。次の保存・入力の変更で消える。
- 各件のテストがあり、単体テスト全件が通る。

- `ConfirmActionDialog` の例外の扱いの変更
- 自動生成の再実行の導線
