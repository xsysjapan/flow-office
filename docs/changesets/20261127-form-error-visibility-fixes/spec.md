## 背景・目的
入力した内容が消える、または失敗が画面に出ないため、利用者が何が起きたか分からない。

## 現状(As-Is)(調査 2026-11-27、investigator。コードの読みによる)

### 1. 経費の申請: 下書きの無い状態の初回の保存で、入力が消える
- `pages/expense/ExpenseClaimNewPage.tsx`:
  - 保存は `ensureClaimId()`(:552-557)で下書きを作り(`createClaim`)、`setClaimId` してから明細を追加する(`addItem`)。
  - `claimId` が付くと `useExpenseClaim(claimId)` の取得が始まり(作成の応答で詳細のキャッシュは作られない)、`if (claimId && isLoadingClaim) return <LoadingState />`(:675)で入力の部分が全部アンマウントされる。
  - そのため、初回の保存では成功・失敗に関わらず入力の部品が1回作り直される。
- 影響:
  - 単票入力(`SingleExpenseItemForm`、値は部品の内部の state)は、明細の追加が 422 になると入力が消え、項目のエラーだけが残る。
  - 表形式(`ExpenseItemsTable`)の行の値はページの state なので残るが、部品の内部の state(選択の行、貼り付け欄、一括の日付・摘要、出発地・到着地の入力 `routeParts`)は消える。`routeParts` が消えて摘要と食い違う恐れがある。
  - まとめて登録のタイトル(`BulkTitleStep`)は `!claimId` で表示しているため、下書きの作成でアンマウントされる。
- ルート(`/expenses/new`)と key(`id ?? 'new'`)は変わらない。原因は読み込み中の表示の条件だけ。

### 2. 備品の詳細: Dialog の入力の検証のエラーが出ない
- `components/ConfirmActionDialog/ConfirmActionDialog.tsx:77-87` は `onConfirm` の例外を握りつぶし(mutation のエラーは `error` prop で出す前提)、Dialog は閉じない。
- `pages/asset/AssetDetailPage.tsx` の4か所が `onConfirm` の中で検証の `Error` を投げるだけで、画面に何も出ず「押しても何も起きない」状態になる:
  - :114 借用者の未選択、:115 承認済みの貸出申請の未選択(貸与)
  - :207 承認者の未選択(貸出の申請)
  - :318 場所の空入力(場所の設定・設置。`confirmDisabled` が無く押せる)
- 同じく `onConfirm` で投げる他の箇所(勤怠の日の削除理由、申請の取消・却下理由、経費の取消理由)は、投げる前に項目のエラーの state を入れて項目の下に出している(変更セット`20261126-field-errors-near-fields`)。

### 3. 働き方の設定: 勤務予定の自動生成の失敗が見えない
- `pages/workCalendar/WorkStylesPage.tsx` の月次の働き方:
  - 保存(`handleSave` :393-412)は、割当(`assignForMonth`)の成功の中で、自動生成(`generateShifts`)を待たずに呼び、続けて確認の表示を閉じる(`setIsConfirming(false)` :407)。
  - 生成の失敗のうち、項目のキーのあるもの(user_id・work_style_id・year_month・from・to)は確認の表示の外の項目の下に出るが、キーの無いもの(`rest`)は確認の表示の中(:499)に描くので、閉じた後は見えない。
  - 生成のエラーは次の操作でも消されず、次に確認の表示を開くと古いエラーが出る見込み(未確認)。
- 割当の失敗は確認の表示が開いたままなので見える。

### 4. 勤怠の日: 休暇の欄の変更で、既存の休暇だけが取り消されて止まる
- `pages/attendance/AttendanceDayPage.tsx` の休暇の欄(`useDayLeaveController` の `apply()` :735-756):
  - 変更があると、先に既存の休暇の申請を取り消し(`cancelExisting()`)、その後で入力を検証して新しい休暇を申請する。
  - 特別休暇の種類が未選択だと、取消の後に `throw new Error('特別休暇の種別を選択してください。')` で止まる。既存の休暇は取り消され(イベントが記録される)、新しい休暇は作られない。
  - 新しい休暇の申請がサーバーで拒否された場合(残数不足・重複など)も、既存の休暇は取り消されたまま残る。
- 呼び出し側(:881-886・:1092-1095)は例外を `setLeaveError` に入れ、まとめての表示に出す。

## 設計前提の検証
- 正データと派生データ: 画面の表示と入力の保持だけ。API・イベントは変えない。
- 原因の分類: 1〜3は実装のミス(表示の条件・例外の扱い・表示の位置)。4は、入力の検証の順序の誤り(実装のミス)に加え、「取消」と「申請」の2つのコマンドを画面が順に呼ぶため、2つ目がサーバーで拒否されると1つ目だけが確定する、という設計の問題を含む(原則9: 操作経路と業務ロジックの分離、原則14: 業務は専用ドメイン)。
- 横展開:
  - 1: 同じ「読み込み中で入力を外す」作りの作成画面が他にあるかを実装時に grep で確かめる(`claimId`/`id` を作成の後に state で付けて同じ画面に留まる作り)。
  - 2: `onConfirm` で検証の Error を投げて state を入れない箇所は、frontend 全体で備品の詳細の4か所だけ(調査済み)。
  - 3: 保存の成功の中で別の mutation を待たずに呼び、表示を閉じる作りが他にあるかを実装時に grep で確かめる。

## 仕様検討

### 論点1: 経費の申請の入力の保持
- 選択肢:
  - A. 読み込み中の表示の条件を変える: 画面を開いたときに既存の下書きを読み込む場合(`/expenses/:id/edit` の初回)だけ全体を読み込み中にし、この画面で下書きを作った後の読み込みでは入力の部分を描いたまま、保存済みの明細・提出の部分だけを読み込み中にする。
  - B. 作成の応答で詳細のキャッシュを作り、読み込み中にならないようにする。
  - C. 単票入力の値をページの state へ持ち上げる。
- 決定: A。
- 理由: 原因(作成の後に入力の部分が外れる)を直接直し、単票・表形式・まとめて登録のタイトルのすべてに効く。B は、作成の応答(`store`)が関連を読み込まない `ExpenseClaimResource` で `items` 等を含まず(確認済み: `ExpenseClaimController.php:88-95`、詳細の `show` は `items.category`・`items.attachments` を読む)、キャッシュに入れると保存済みの明細の表示が壊れる。C は単票にしか効かない。
- 全体を置き換えるエラーの表示(`if (claimId && claimError)`)も同じく入力を外す(作成の後の取得の失敗、明細の追加の後の再取得の失敗。react-query v5 はデータを持ったまま `error` を立てる)。全体のエラーは「ルートの `id` があり、データが無く、エラーがある」ときだけにし、それ以外は保存済みの明細の場所に出す。
- 下書きの作成が成功して明細の追加が 422 になったとき、空の下書きがサーバーに残る(今と同じ)。画面は作成済みの下書きの編集として続けられるので、そのままにする(下書き一覧から削除できる)。
- 未確定・要確認事項: なし

### 論点2: 備品の詳細の Dialog の検証
- 選択肢:
  - A. `ConfirmActionDialog` が `onConfirm` の検証の例外を受けて表示する仕組みを足す(検証用の例外の型と mutation の失敗を区別する)。
  - B. 他の箇所と同じ形にする: 投げる前に項目のエラーの state を入れ、その項目の `FormField` の `error` に出す(送信を押した後に出し、入力すると消す)。
  - C. 確定のボタンを `confirmDisabled` で押せなくする。
- 決定: B。
- 理由: 既に4画面で使っている形と揃い、§2.19(エラーは項目の近く)に合う。A は共有の部品の作りを変え、全 Dialog に影響する。C は何が足りないかの文が出ない。
- 再発の防止: 仕様確定事項5。
- 未確定・要確認事項: なし

### 論点3: 働き方の自動生成の失敗の表示
- 選択肢:
  - A. 生成の失敗(項目に出ないもの)を、確認の表示の外(月次の働き方の欄の、保存のボタンの位置)に `ErrorMessage` で出す。次の保存・入力の変更で生成のエラーを消す(`generateShifts.reset()`)。
  - B. 割当→生成を順に待ち、生成が失敗したら確認の表示を開いたままにする。
  - C. 失敗をトーストで通知する。
- 決定: A。
- 理由: 割当は既に保存されているので、確認の表示を開いたままにする(B)と「保存できていない」と誤解させ、再実行で割当をもう一度送る(冪等か未確認)。A は失敗を確実に見せ、割当が保存済みであることと矛盾しない。トースト(C)は消えるので失敗の表示に向かない(§2.12 は失敗を操作の直近の `ErrorMessage` で返す)。
- 文言: `ErrorMessage` の上に `<p>`「働き方は保存しましたが、勤務予定の自動生成に失敗しました。」を添える(`ErrorMessage` に前置きの仕組みは無い)。
- 未確定・要確認事項: なし

### 論点4: 勤怠の日の休暇の取消の順
- 選択肢:
  - A. 画面の検証を取消より前に移す(特別休暇の種類の未選択など、画面で分かる不足は取消の前に止める)。
  - B. backend に「休暇の変更」(取消と申請を1トランザクションで行う)のコマンド・API を作り、画面はそれを1回呼ぶ。
- 決定: A を本変更で行う。B は別の変更セットの候補として記録し、ユーザーに報告する。
- 理由: 今回の不具合(画面で分かる不足で既存の休暇が消える)は A で確実に防げ、画面の中で完結する。B はサーバーの拒否(残数不足・重複)でも既存の休暇が残るようにする正しい直し方だが、3種類の休暇のドメイン(有給・特別休暇・代休)に変更のコマンドを足す設計の検討が要り、本変更(画面の不具合の修正)の範囲を超える。
- 表示: 特別休暇の種類の未選択は、送信を押した後にその項目(特別休暇の種類)の下に出す(§2.19。論点2と同じ「送信を押したか」の形)。
- B はユーザーの判断(2026-11-27)で行う。日の勤怠の保存も同じトランザクションに含める。別の変更セット(`20261127-attendance-day-atomic-save`)で扱う。本変更の A(画面で分かる不足を先に確かめる)は、B の後も送信前の確認として残す。
- 未確定・要確認事項: なし

## 仕様確定事項(まとめ)
1. `ExpenseClaimNewPage`:
   - 全体の読み込み中: `routeClaimId && isLoadingClaim` のときだけ(v5 の `isLoading` はデータが無いまま取得中の間だけ真。`claimId` は一度決まると変わらない)。
   - 全体のエラー: `routeClaimId && !claim && claimError` のときだけ。それ以外の `claimError` は、保存済みの明細の場所に `ErrorMessage`(「経費精算の取得に失敗しました。」)で出し、入力の部分は残す。
   - この画面で作成した後の読み込み中(`claimId && !claim && isLoadingClaim`)は、保存済みの明細の場所に `LoadingState` を出す。この場所は区分を選ぶ前の分岐と入力の分岐の2か所にあるので両方に入れる。入力の部分(単票・表形式・まとめて登録のタイトル)はアンマウントしない。
   - `BulkTitleStep` の表示の条件を `!routeClaimId && entryMode === 'bulk' && !bulkTitleDone` にし、`startClaimTitle` が成功したら `bulkTitleDone = true`。下書きを作った後(`claimId` がある)は、タイトルの手順の「登録方法の選択に戻る」を出さない(戻ると区分の選択へ進んでしまい戻る導線が無くなるため。タイトルの失敗はその場で再送信する)。これで、作成は成功しタイトルが失敗したときにタイトルの失敗が見えない今の問題も直る。
   - 保存の後に待たずに呼んでいる `void startClaimTitle.mutateAsync(...)`(タイトルの自動の提案、:620・:636)は `.catch(() => undefined)` で黙って無視する(タイトルは任意で後から編集でき、未処理の reject を出さないため)。
   - 離脱警告(`useUnsavedChangesGuard`・`navigateAfterSave`)と項目エラー(`fieldErrors`)は壊さない。
2. `AssetDetailPage` の4か所:
   - state は各 Dialog の部品(`LendAssetDialog`・`AssetLoanRequestDialog`・`LocationTextDialog`)の中に「送信を押したか」(`submitted`)として持つ。表示は「送信を押した後、かつ値がまだ空」(例: `submitted && !loanRequestId`)のとき、その項目の `FormField` の `error` に文を出す(値を選べば自然に消え、自動選択でも消える)。サーバーの項目エラーとは `localError ?? of(key)` で並べる。
   - 開いたときに `submitted` を false に戻し、mutation の `reset()` も呼ぶ(開き直したときに前回のサーバーの 422 が残る今の問題も直す)。`LocationTextDialog` は mutation をページが持つので、開いたときに呼ぶ `onOpen` を受け取る。
   - 借用者を変えたら申請の選択と申請のエラーも消す(今の挙動に合わせる)。
   - `LocationTextDialog` は通常配置場所・設置・移設の3か所で使われ、3か所とも直る。
3. `WorkStylesPage`:
   - `generateShifts.error` があるときは、キーの有無に関わらず、確認の表示の外(保存のボタンの位置)に `<p>`「働き方は保存しましたが、勤務予定の自動生成に失敗しました。」と `ErrorMessage`(エラー全体)を出す。項目の下(`errorOf`)には割当のエラーだけを出す(保存の後に年月が空になるので、生成のキー付きのエラーを項目の下に出すと文脈が無くなるため)。
   - 生成中(`generateShifts.isPending`)は同じ位置に「勤務予定を生成しています。」を出す。
   - `generateShifts.reset()` は、保存の開始・社員・年月・働き方の各ハンドラの中で直接呼ぶ(effect では呼ばない。保存の成功で年月を空にするときに、始めたばかりの生成の結果を捨てないため)。生成中は呼ばない。
4. `AttendanceDayPage` の `useDayLeaveController`:
   - `apply()` の入力の検証(特別休暇の種類の未選択、ほか画面で分かる不足があれば同じく)を `cancelExisting()` より前に行う。不足があれば何も取り消さずに止める。
   - 未選択のエラーは、送信を押した後に特別休暇の種類の `FormField` の下に出す(まとめての表示には出さない)。
   - 日の編集・作成の保存の流れ(日の保存と休暇の適用の順)は変えない。
5. 横展開の grep(1・3)で同じ作りが見つかれば、実装結果に記録し、同じ直し方を当てる(見つからなければ「無し」と記録)。
6. スキル: `ui-interaction-patterns` §2.19 の既存の行「理由の必須などのクライアントの検証も、送信を押した後にその項目の下に出す」に、「`ConfirmActionDialog` の `onConfirm` で Error を投げるだけでは握りつぶされる。送信を押した状態を持ち、開いたときに消す」を加える(新しい行は足さない)。

## 受け入れ条件
- 経費の申請で、下書きの無い状態から単票を保存して 422 になっても、入力が残り、項目の下にエラーが出る(離脱警告も効く)。表形式の出発地・到着地の入力、まとめて登録のタイトルも、初回の保存で消えない。下書きの取得・再取得が失敗しても入力は残り、保存済みの明細の場所にエラーが出る。
- 備品の詳細の貸与・貸出の申請・場所(通常配置場所・設置・移設)の Dialog で、未選択・未入力のまま確定すると、その項目の下にエラーが出る。開き直すと前回のエラーは出ない。
- 勤怠の日で、既存の休暇がある日に特別休暇へ変え、種類を選ばずに保存すると、既存の休暇は取り消されず、特別休暇の種類の下にエラーが出る。
- 働き方の設定で、割当が成功し自動生成が失敗すると(キーの有無に関わらず)、確認の表示を閉じた後も失敗の文とエラーが見える。次の保存・入力の変更で消える。
- 各件のテストがあり、単体テスト全件が通る。

## 対象外
- 下書きの作成と明細の追加を1回の API にまとめること(backend の変更)
- `ConfirmActionDialog` の例外の扱いの変更
- 自動生成の再実行の導線
- 経費の申請で、明細の追加は成功し領収書のアップロードが失敗したとき、入力が残ってもう一度押すと明細が二重に作られる(2回目以降の保存では今も起きる既存の問題。本変更で初回の保存でも起きるようになる)。別の候補として記録する。
- 日の勤怠の保存・休暇の取消・休暇の申請を backend の1トランザクションにすること(論点4の B)。変更セット`20261127-attendance-day-atomic-save`で扱う。
