## 調査結果と決定

### 論点1(#3): 内部コードの表示名
- 調査で見つかった、コードをそのまま出している箇所と決定:

  | 箇所 | 値 | 決定 |
  |---|---|---|
  | タスク一覧・タスク詳細の「種別」(`BackOfficeTaskListPage.tsx:107`、`BackOfficeTaskDetailPage.tsx:183`) | `attendance_month_confirmation`・`expense_reimbursement`、申請種別で自由に設定する値 | 既知のコードは表示名にし(「月次勤怠の確定」「経費の精算」)、未知のコードはそのまま出す関数にする。申請種別の設定の値は、管理者が付けた語として表示する |
  | グループ一覧の状態(`UserManagementAccessPage.tsx:350`) | `active`・`inactive` | 「有効」「無効」 |
  | 所属の区分(`GroupDetailPage.tsx:421`) | `primary`・`member` | 「主所属」「所属」にする。直後の主所属の表示と重なるなら1つにまとめる |
  | 運用コマンドの実行の状態(`AdminCommandsPage.tsx:112`) | `queued` ほか(実装時に列挙) | 表示名にする(「待機中」「実行中」「成功」「失敗」など) |
  | シフトの日の区分(`ShiftsPage.tsx:123`) | `weekday`・`legal_holiday`・`company_holiday`・`special_working_day` | 「平日」「法定休日」「所定休日」「特別稼働日」(既存の勤怠の語と揃える) |
  | 利用者の管理元(`UserListPage.tsx:481`) | `local`・`external_hr` | 「ローカル」「外部人事」(既存の画面の語と揃える) |
  | タスクの元データ(`BackOfficeTaskDetailPage.tsx:186`) | `attendance_month` ほか | 表示名にする(「月次勤怠」「申請」など。実装時に列挙) |
  | 項目の管理元のキー(`UserManagementAccessPage.tsx:526,1027`) | 利用者の項目のキー | 項目名にする(実装時に列挙。項目名は社員一覧のラベルと揃える) |

- 意図して出しているコード(コード列: 勤務形態・ロール・申請種別・経費区分・シフトのパターン、運用コマンド名)と、監査ログの集約・イベントの種別は対象外にする。自由入力の文字列も対象外。
- 表示名の関数は `utils/statusLabels.ts` に置き、既知の値と未知の値のテストを `statusLabels.test.ts` に足す。
- 規則: 画面に API の列挙値を出すときは、表示名の関数を通す。`ui-interaction-patterns` に1行足す。

### 論点2(#4): 備品のナビの入口ごとの条件
- 決定:
  - 「備品貸出」(申請のグループ): `/assets?management_type=lending&lending_status=available` を開く。利用可能な貸出品で、セルフ貸出も承認制も含む。
  - 「備品管理」(業務のグループ): `/assets` を開く(今のまま)。
- 選択状態の判定: ナビの項目に `matchQuery`(一致させるクエリ)を足す。パスが一致し、`matchQuery` のキーがすべて一致する項目のうち、一致したキーの数が最も多い項目だけを選択状態にする。
  - 備品貸出の条件で開くと、備品貸出だけが選択状態になる。
  - 条件を外したり変えたりすると、備品管理が選択状態になる。
- 見出し・パンくずは「備品管理」のまま(ページは同じ一覧)。
- 変更セット`20260831-asset-management-refinement`の論点8(備品貸出は絞り込み無しで `/assets` へ)を、本決定で改める。向こうの spec に追記する。
- テスト:
  - ナビの選択状態の判定を関数にして、単体テストを書く。パスだけの項目、クエリの一致、同じパスの複数の項目。
  - `AppLayout` のテストで、2つの URL それぞれで選択状態になる項目を確かめる。

### 論点3(#5): 空の選択列
- 原因: 申請一覧の選択列の見出しは、条件無しで描画されている。本体のチェックボックスは取り消せる行にだけ出るので、取り消せる行が無い一般の社員には、空の列が残る。
- 同じ形の画面: 承認一覧、付与予定。タスク一覧は、条件で見出しと本体の両方を出し分けている(正しい形)。
- 決定: 3画面とも、選択できる行が1つでもあるときだけ、選択列(見出しと本体)を出す。タスク一覧の形に揃える。
- テスト: 各画面のテストに、次の2つを足す。
  - 選択できる行が無いと、列が出ない。
  - 選択できる行があると、列が出る。

### 論点4(#2): 横スクロールの手がかり
- 決定: 共通の表(`ui/table.tsx`)で、横にはみ出しているときだけ、はみ出している側の端に影を出す。
  - 方式: 小さな hook(`useOverflowEdges`)が、スクロールとサイズの変化を見て、`data-overflow-start`・`data-overflow-end` を表の外枠に付ける。Tailwind の `data-[...]` で影を出す。列の構成は変えない。
  - CSS だけの方式(background-attachment)は使わない。jsdom で確かめられず、単体テストで保証できないため(原則16)。
- テスト(単体): `scrollWidth`・`clientWidth`・`scrollLeft` を差し替え、次を確かめる。
  - はみ出していないと属性が無い。
  - 左端では end だけ、途中では両方、右端では start だけが付く。
- 見た目は Storybook で確かめる(社員一覧の12列の例を story に足す)。
