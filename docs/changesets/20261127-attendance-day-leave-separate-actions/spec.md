## 背景・目的
画面には休暇の欄が無いのに、保存の後に休暇の処理が動き、利用者が何もしなくても承認済みの休暇が取り消されることがある(下の「現状」)。この処理を消して、勤怠の保存は日の勤怠だけにする(設計原則17)。あわせて、休暇の操作の入口である「この日の操作」のメニューの取消を、1日に複数ある休暇・申請中の休暇に対応させる。

- 休暇の取消の API(`POST /*/requests/{id}/cancel`)は1つのコマンド。申請中・差し戻し・承認済みを取り消せ、本人の確認がある。申請中・差し戻し中の取消はワークフローの取消に連鎖する(承認済みのワークフローは変えない)。締め済みの日は 422。
- 差し戻しの時点で休暇ビューから外れるため、差し戻し中の休暇は勤怠の日の画面には出ない(各休暇の画面で取り消す)。
- 各休暇の画面(本人)の申請の一覧は、取消を申請中・差し戻しに出し、承認済みには出していない(`MyPaidLeavePage.tsx:325` 等)。
- 休暇だけの日(`source=leave`)は、休暇を取り消すと勤怠の日そのものが削除される(`docs/07`「休暇と勤怠日の関係」)。編集中に取り消すと、編集のフォームが消えて未保存の入力が失われる。
- 週次の勤怠・週次/月次の一括入力に休暇の欄は無い(確認済み)。E2E に「この日の操作」の休暇の項目を使う spec は無い(grep で0件)。勤怠の日を通る spec は scenario-02・06・99。

## 設計前提の検証
- 正データと派生データ: 休暇の正は休暇の文脈、勤怠の休暇ビューはその派生。勤怠の保存から休暇の処理を消すと、勤怠の画面の保存は休暇を変えない(docs/07 と一致)。
- 原則17: 勤怠の保存・休暇の申請・休暇の取消が、それぞれ1回の操作で1つのコマンドになる。
- 原因の分類: 休暇の欄を消したときに処理を消し忘れた実装のミス(画面に見えない処理が動く)。設計の誤りではない。
- 管理者の経路: 勤怠の日の画面は本人専用で、管理者が他人の休暇を操作する経路は今も無い。失われる機能は無い。

## 仕様検討

### 論点1: 勤怠の日の保存に残る休暇の処理
- 決定: `useLeaveDesignationController`・`detectLeaveDesignation`・`apply()` の呼び出し・`leaveError` の表示を削除し、保存は日の勤怠だけにする。離脱警告の dirty の判定(`attendanceDayDirty.ts`)から休暇の項目を外す。
- 理由: 画面に欄が無いのに動く処理で、承認済みの休暇を消す不具合の原因(現状)。ユーザーの判断(休暇は保存で扱わない)。
- 未確定・要確認事項: なし

### 論点2: 「この日の操作」のメニューの取消
- 決定:
  - 取消の項目は、休暇ビュー(`day.leaves`)の有効な休暇(申請中・承認済み)ごとに1つずつ出す(1日に複数の休暇があってもすべて出す)。文言は「{休暇の名前}を取り消す」(例: 「有給休暇(午前半休)を取り消す」「特別休暇(慶弔)を取り消す」)。「承認を取り消す」の文言は使わない(原則13)。
  - 取消の対象の ID は `day.leaves` の `request_id` を使う。本人の申請の一覧の3つの取得(`useMy*LeaveRequests`)は、他で使っていなければ外す。
  - 差し戻し中の休暇は休暇ビューに無いので出さない(各休暇の画面で取り消す)。
  - 確認は `ConfirmActionDialog`(共通の確認の部品。§2.12)に置き換え、`CancelApprovedLeaveDialog` は削除する。タイトル「{休暇の名前}を取り消しますか?」、本文は状態で分ける: 承認済みは「取り消すと、消化した残数が戻ります。」、申請中は「取り消すと、承認の依頼も取り消されます。」。確定のボタン「取り消す」(`confirmVariant="danger"`)。成功のトーストは「{休暇の名前}を取り消しました」。失敗(締め済み等の 422)は Dialog の `error` に出す。
  - 編集・作成のフォームを開いている間は、取消の項目を押せなくし、理由「編集を保存するか、キャンセルしてから取り消してください。」を出す(休暇だけの日は取消で勤怠の日が消え、未保存の入力が失われるため)。
  - 締め済みの日(画面の `locked`)は、取消の項目を押せなくし、理由を出す(§2.14・§2.25。422 に任せない)。
- 未確定・要確認事項: なし

### 論点3: 「この日の操作」のメニューの申請
- 決定: 今のまま(各休暇の画面へ日付付きで移る)。特別休暇の申請の項目は、有効な特別休暇の種類が無いときは出さない(週次の選択バーと同じ)。
- 未確定・要確認事項: なし

### 論点4: 取消の置き場所の分担
- 事実: 本人の取消は、承認済み=勤怠の日の画面だけ、差し戻し=各休暇の画面だけ、申請中=両方、となる。
- 決定: 本変更ではこの分担のままにし、各休暇の画面の取消の条件(承認済みにも出すか)をそろえる件は、別の変更セットの候補として記録する。
- 理由: 本変更の目的(保存の不具合の修正と、メニューを1日に複数の休暇・申請中に対応させる)を超える。
- 未確定・要確認事項: なし

### 論点5: 関連する変更セットとdocs
- 変更セット`20261127-form-error-visibility-fixes`から、休暇の件を外すことは反映済み(`bf10da00`)。向こうの「4件目」の説明(欄で特別休暇を選んで保存すると…)は、欄が見える前提の誤りだったので、本変更の「現状」の経路に直す。
- `docs/09`:594 の「承認済み申請のみ取消可能」を、:312・:329 に合わせて「申請中・承認済みを取り消せる」に直す(本変更で勤怠の日の画面から申請中も取り消せるようになるため)。

## 受け入れ条件
- 勤怠の日の保存は日の勤怠だけを保存し、休暇の API を呼ばない(申請の一覧の読み込み中に保存しても既存の休暇が消えない)。
