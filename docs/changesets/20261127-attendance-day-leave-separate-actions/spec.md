# attendance-day-leave-separate-actions(勤怠の日の保存から休暇を外し、休暇の登録と取消を別々の操作にする)

ステータス: 検討中

## 変更要望(原文)
> 今後のためにルールとしてAPI呼び出しは基本的に一コマンドのみ処理することと、改めてコレオグラフィーの整合性で実装できないか試すことをお願いします
> 基本的に休暇の種類を切り替えるという運用が微妙ですね。きっぱり登録と取消しは別操作にしてください。

画面の扱い(ユーザーの回答 2026-11-27): 「勤怠の日の画面に別ボタンで残す」。勤怠の「保存」は日の勤怠だけを保存し、休暇は扱わない(1回の操作=1つのコマンド)。

## 経緯
- 変更セット`20261127-form-error-visibility-fixes`の論点4で、勤怠の日の保存の後に休暇の取消・申請を順に送るため、途中で止まると承認済みの休暇が黙って消える不具合を見つけた。
- 1回の保存で取消と申請を整合させる案(API で束ねる案、イベントの連鎖の案)を検討した(この変更セットの旧名 `20261127-attendance-day-leave-switch`。git の履歴に残る)。
- ユーザーの判断で、休暇の種類を切り替える運用自体をやめ、休暇の登録と取消を別々の操作にした。各操作が1つのコマンドなので、途中で止まって一部だけ確定することが無い。

## 背景・目的
勤怠の日の保存1回が「日の勤怠」「元の休暇の取消」「新しい休暇の申請」の3つの確定を含むのをやめ、1回の操作が1つのコマンドになるようにする(設計原則17)。

## 現状(As-Is)
- `frontend/src/pages/attendance/AttendanceDayPage.tsx`:
  - 日の編集(`DayEditForm`)・作成(`DayCreateForm`)に「休暇」の欄がある(`useLeaveDesignationController` :672-760)。保存が成功した後に、変更があれば元の休暇の取消(`Cancel{X}LeaveRequest` の API)と新しい休暇の申請(`Request{X}Leave` の API)を順に送る(:881・:1092)。
  - 画面の右上の「この日の操作」のメニュー(:1554-1597)に、すでに次の別々の操作がある:
    - 「有給休暇を申請する」「特別休暇を申請する」「代休を申請する」: 各休暇の画面へ、日付を入れて移る(`/paid-leave?date=…` 等)。
    - 「有給休暇の承認を取り消す」等: 承認済みの休暇があるときだけ出る。確認の Dialog で取消の API を1回呼ぶ(`setCancelTarget`)。申請中(未承認)の休暇は出ない。
  - 休暇の表示: 勤怠の休暇ビュー(`day.leaves`)。
- backend: 休暇の申請・取消の API はそれぞれ別。申請の API は承認不要の設定のとき Controller で申請→承認の2つのコマンドを束ねている(設計原則17の既存の例外。本変更の対象外)。
- docs: `docs/07-usecases-attendance.md`「休暇と勤怠日の関係」は休暇の正を休暇の文脈に置き、勤怠は休暇ビューで判定すると書いている。勤怠の日の保存で休暇を申請・取消することは docs に書かれていない(画面のコメントだけ)。

## 設計前提の検証
- 正データと派生データ: 休暇の正は休暇の文脈(申請・消化)、勤怠の休暇ビューはその派生。勤怠の日の保存から休暇を外すと、勤怠の画面は休暇を変えない(docs/07 の記述と一致する)。
- 原則17: 勤怠の保存(1つのコマンド)、休暇の申請(1つの操作)、休暇の取消(1つのコマンド)がそれぞれ別の操作になる。
- 横展開: 週次の勤怠(勤怠の日の編集ビュー)・月次の一括入力に休暇の欄があるかを実装時に確かめる。あれば同じく外す。

## 仕様検討

### 論点1: 勤怠の日の保存
- 決定: 日の編集・作成のフォームから「休暇」の欄を外し、保存は日の勤怠だけにする(`useLeaveDesignationController` を削除)。
- 理由: ユーザーの判断。1回の操作=1つのコマンド(原則17)。
- 離脱警告の dirty の判定(`isDayFormDirty`)から休暇の欄の項目を外す。
- 未確定・要確認事項: なし

### 論点2: 休暇の登録
- 選択肢:
  - A. 今のメニューのまま、各休暇の画面へ日付を入れて移る(「〜を申請する」)。
  - B. 勤怠の日の画面の中に Dialog を作り、その場で申請する。
- 決定: A。
- 理由: 休暇の申請の画面には、承認者の指定・残数の表示・時間単位・まとめ申請などの入力がすでにそろっている。B は同じ入力を勤怠の画面に二重に作ることになる。申請の画面から戻ると勤怠の日の画面に戻れる(既存の `state` の受け渡し)。
- 置き場所: メニューの中だけでなく、休暇の表示の近く(休暇の無い日は「休暇を申請する」の入口)からも辿れるようにする(論点4)。
- 未確定・要確認事項: なし

### 論点3: 休暇の取消
- 決定:
  - その日の休暇ごとに「取消」を出す。対象は承認済みに加え、申請中の休暇も含める(今は承認済みだけ)。確認の Dialog で取消の API を1回呼ぶ(今の `setCancelTarget` の流れを使う)。
  - 文言を「〜の承認を取り消す」から「〜を取り消す」にする(承認という行為は取り消さない。原則13。実際の操作は休暇の申請の取消)。Dialog の文言も同じく直す。
  - 締め済みの月などで取り消せない場合は、API の 422 を Dialog に出す(今のまま)。
- 未確定・要確認事項: なし

### 論点4: 休暇の表示と操作の置き場所
- 決定:
  - 勤怠の日の画面の休暇の表示(その日の休暇の一覧)の各行に「取消」のボタンを置く。休暇の表示の近くに「休暇を申請する」(有給・特別休暇・代休を選ぶメニュー。各休暇の画面へ移る)を置く。
  - 右上のメニューの休暇の項目(申請・取消)は、上の置き場所と重複するので外す(振替休日の項目は残す)。
  - 編集・作成のフォームを開いている間も、休暇の表示と操作は使える(保存とは別の操作)。ただし未保存の入力がある状態で休暇の画面へ移ると、離脱警告が出る(既存の仕組み)。
- 理由: 休暇の状態を見ている場所で、その休暇の操作ができるようにする。メニューの中に隠さない。
- 未確定・要確認事項: なし

### 論点5: 関連する変更セットとの関係
- 変更セット`20261127-form-error-visibility-fixes`の論点4(休暇の欄の入力を先に確かめる)は、休暇の欄が無くなるので不要になる。向こうの spec から論点4を外し、本変更セットへの参照に置き換える。
- 未確定・要確認事項: なし

## 仕様確定事項(まとめ)
- `AttendanceDayPage.tsx`:
  - `DayEditForm`・`DayCreateForm` から休暇の欄と `useLeaveDesignationController`・`detectLeaveDesignation` を削除し、保存は日の勤怠だけ。保存の後の `leaveController.apply()` と `leaveError` の表示を削除する。
  - `attendanceDayDirty.ts` の dirty の判定から休暇の項目を外し、テストを直す。
  - 休暇の表示の各行に「取消」(承認済み・申請中)。確認の Dialog の文言は「{休暇の名前}を取り消しますか?」、確定のボタンは「取り消す」(`confirmVariant="danger"`)。成功は `notify.success`。
  - 休暇の表示の近くに「休暇を申請する」のメニュー(有給休暇・特別休暇・代休。今のリンクと同じ移動先と `state`)。
  - 右上のメニューから休暇の申請・取消の項目を外す。
- 週次・月次の一括入力に休暇の欄があれば同じく外す(無ければ実装結果に「無し」と記録)。
- backend: 変更なし。
- テスト(Vitest):
  - 日の編集・作成の保存で、休暇の API を呼ばない。
  - 休暇の表示の「取消」(承認済み・申請中)で取消の API を1回呼ぶ。422 が Dialog に出る。
  - 「休暇を申請する」から各休暇の画面へ日付付きで移る。
  - 右上のメニューに休暇の項目が無い。
- E2E: 勤怠の日の画面で休暇を操作している spec を grep し、新しい置き場所に合わせて直す。流すのはその spec と、勤怠の日を通る spec だけ。

## 受け入れ条件
- 勤怠の日の保存は、日の勤怠だけを保存する(休暇の API を呼ばない)。
- 休暇の登録は各休暇の画面(1回の操作)、取消は勤怠の日の画面の休暇の行の「取消」(1回の操作)で行える。
- 「承認を取り消す」という文言が画面に無い。
- 単体テスト全件と、対象の E2E が通る。

## 対象外
- 休暇の申請の API の、承認不要の設定での申請→承認の束ね(原則17の既存の例外。別の是正の変更セット)
- 勤怠の日の画面の中で休暇を申請する Dialog
- 休暇の種類を1回で切り替える操作

## ドキュメントへの影響
