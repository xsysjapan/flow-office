## 不具合1: scenario-10 のグループの新規作成(全件実行で毎回失敗、単独では通る)
- 調査結果(コードとログの読解):
  - 失敗の時点で、一覧の「新規作成」を押した後も、画面が一覧のままだった。
    - 次の `getByLabel('グループ種別')` は、作成フォームではなく一覧の絞り込みに当たった。2つが同じラベルのため。
    - そのまま「名称」を5分待って失敗した。
  - 一覧の絞り込みは URL だけで持ち、前のテストから引き継がれない。遷移を取り消すコード(ガード・自動の遷移・URL の書き戻し)は見つからなかった。
  - 押下が遷移を起こさなかった原因は、トレースが残っておらず特定できていない。製品側の原因は見つかっていない。
- 決定:
  1. テストを確実にする。
     - 押した直後に URL(`/admin/groups/new`)と見出し「グループを作成」を待ってから入力する。
     - 入力はフォームの範囲(見出しの region)に限る。
  2. 製品側の確認を単体テストで足す。Vitest の画面の統合テストで、一覧(`/admin/groups`)の「新規作成」を押すと、作成画面に移り「名称」が出ることを確かめる。今は無い。
  3. 失敗したときの原因を後で追えるよう、この spec だけ trace を `retain-on-failure` のまま残す(既定どおり)。
- 検証: 修正の後、E2E の全件を1回実行する(この不具合は全件の実行でしか起きないため。ユーザーの方針の例外として、この変更セットの検証に限る)。
  - 通らなければ、trace で押下の直後を確かめて原因を特定する。製品の不具合なら直す。

## 不具合2: scenario-99 §5-3・§5-8(日本時間の0時をまたぐと422)
- 原因:
  - 同じ実行の前段(scenario-09)で、同じ社員の当月を締めている。
  - 0時をまたいで「今日」が変わると、補助の関数 `ensureTodayClockedOut` が新しい日に出勤の打刻を試す。その日は締め済みの月に入るので、422 で拒否される(仕様どおり)。
  - テスト側の問題で、製品の不具合ではない。
- 決定:
  - §5-3・§5-8 を「今日」に依存させない。テスト用の固定の年月・勤務日を使い、日次を作成 → 提出・承認 → 締める。
  - 他の spec が使う年月(scenario-09 の 2026-05・2026-06 など)とは重ならない月にする(grep で確かめる)。
- 同じ形の scenario-09(:337・:391、「今日の当月を締める」)も、同じ境界で将来同じ失敗を起こしうる。今回は失敗していないが、同じく固定の年月に直す。
