# leave-cancellation-request(段階③c: 承認済みの休暇の取消を、承認の設定に従って取消の申請にする)

ステータス: レビュー中

## 変更要望と決定(ユーザーの回答 2026-11-28)
- 承認済みの休暇の取消は、休暇の種類の承認の設定に従う: 承認不要なら直接取り消す。承認が必要なら取消の申請を出す(休暇申請の承認の取消ではない。原則13)。
- 取消は申請の単位(期間全体)。
- 取消の申請の自己承認(申請者が自分を承認者にするとその場で承認)は、他の申請と同じにする。
- 前提: ③a(`20261128-returned-is-final`、差戻しは最終)と ③b(`20261128-period-leave-request`、期間の申請)の後に行う。

## 現状(As-Is)
- 申請者・管理者は、申請中・承認済みの休暇を直接取り消せる(承認済みは残数を戻す。承認済みのワークフローは取り消さない)。各休暇の画面の取消は申請中だけ(③a で差戻しを外した後)、勤怠の日の画面は申請中・承認済み(`20261127-attendance-day-leave-separate-actions`)。
- 承認の要否は休暇の種類ごとの全体の設定で、入口は呼び出し側が選び、Handler が設定に応じて拒否する(`LeaveApprovalRequirement`、`20261128-single-command-entrypoints`)。
- 前例の「取消の依頼」: 勤怠確定取消依頼(`AttendanceMonthRevertOnConfirmationRevertRequestApprovedReactor`)は汎用の申請種別に form_data を持たせ、承認時にだけ判定し `workflow_requests` を読む。本変更ではこの形に倣わない(設計レビュー H4)。
- 既存の `paid_leave_request` の subject を取消の申請に使い回すと、下書きの Reactor・対応表・取下げ・差戻しの連鎖が元の休暇に作用し、承認なしで休暇が取り消される・差戻しができない(設計レビュー H4 で経路を確認)。
- 休暇の解除は管理者の例外なしで締めの判定を通る(`AttendanceEditGuard`)。月次の提出のガード(`PaidLeaveApprovalGuard`)は有給の申請中しか見ない。

## 設計前提の検証
- 原則13: 取消の申請は新しい状態遷移。休暇の承認のイベントは書き換えない。
- 原則14: 取消の申請はワークフローの1種類(業務の対象は既存の休暇の申請)。取消の業務の判定・処理は休暇の文脈の集約に置く。
- 原則15: 休暇の文脈は自分の集約・テーブルだけを書く。ワークフローとはイベントで連携する。

## 仕様検討

### 論点1: 取消の申請の形
- 決定:
  - 休暇の種類ごとに専用の subject_type を作る(`paid_leave_cancellation`・`special_leave_cancellation`・`compensatory_leave_cancellation`)。subject_id は元の休暇の申請の ID。対応表(`LeaveRequestWorkflowLinks`)に用途の列(申請・取消)を足す。
  - 休暇の文脈に、取消の申請のワークフローの下書きを受ける Reactor と、集約のコマンド `RequestCancellation` を置く。集約が次を判定する: 承認済みであること、取消の申請中でないこと(2つ目の禁止)、どれか1日でも締められていないこと(締められた日を含む休暇は取消の申請を出せない)。
  - 取消の申請が承認されたら、集約が休暇を取り消す(取消の理由は「取消の申請の承認による取消」)。差し戻された・取り下げられたら、集約に「取消の申請が終わった」を記録する(休暇はそのまま)。
  - 承認の設定: 取消の時点の設定で判断する。入口は呼び出し側が選ぶ(承認不要: 直接の取消 `POST /{kind}/requests/{id}/cancel`、承認が必要: 取消の申請 `POST /{kind}/requests/{id}/cancellation-requests`)。Handler が設定に応じて拒否する(段階①と同じ作り)。
  - 管理者の取消(`admin-cancel`)は今と同じく直接。
- 未確定・要確認事項: なし

### 論点2: 他の経路との関係
- 決定:
  - 取消の申請中に、休暇が別の経路(管理者の取消)で取り消されたら、申請中の取消の申請を自動で取り消す(逆方向の連携。docs/03 3.10 の逆方向の一覧に足す)。
  - 月次の提出のガードに、取消の申請中の休暇を加える(有給・特別休暇・代休)。取消の申請中の休暇がある月は提出できない(先に承認・差戻しを済ませる)。
  - 自己承認は他の申請と同じ(申請者が自分を承認者にするとその場で承認され、休暇が取り消される)。
- 未確定・要確認事項: なし

### 論点3: 画面
- 決定:
  - 各休暇の画面の申請一覧と、勤怠の日の画面の「この日の操作」で、承認済みの休暇に「取り消す」(承認不要)または「取消を申請する」(承認が必要。承認者を選ぶ Dialog)を出す。申請中の休暇には「取り下げる」(申請全体)。取消の申請中の休暇には「取消を申請中」と出し、操作を出さない。
  - 締められた日を含む休暇は、押せずに理由を出す。
  - 承認の画面: 取消の申請の内容(元の休暇の期間・種類・日数)を出す。
- 未確定・要確認事項: なし

## 仕様確定事項(まとめ)
(設計レビューの後に確定する)
- backend: subject_type・対応表の用途の列・休暇の集約の取消の申請のコマンドとイベント(取消の申請の開始・終わり)・下書き/承認/差戻し/取下げを受ける Reactor・入口・管理者の取消での自動の取下げ・月次の提出のガード。
- frontend: 休暇の3画面・勤怠の日の画面の操作、承認の画面の取消の申請の表示。
- テスト(業務シナリオのテスト): 承認が必要な設定で取消の申請→承認で休暇の取消・残数が戻る・休暇ビューから外れる/差戻し・取下げで休暇がそのまま/2つ目の取消の申請の拒否/締められた日を含む休暇の拒否/承認不要の設定で直接の取消、取消の申請の入口は拒否/管理者の取消で取消の申請が自動で取り下げられる/取消の申請中の休暇がある月は提出できない/自己承認/作り直しで同じ状態。

## 受け入れ条件
- 承認済みの休暇を、承認不要なら直接、承認が必要なら取消の申請で、申請の単位で取り消せる。取消の申請の差戻し・取下げで休暇は残る。
- 取消の申請が元の休暇の申請の連鎖に作用しない(承認なしで取り消されない)。
- 上のテストと全件の単体テスト、変えた画面を通る E2E の spec が通る。
