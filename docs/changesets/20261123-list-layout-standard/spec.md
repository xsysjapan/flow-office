> 現在作業中の変更記録について画面のレイアウト崩れや変なレイアウトがないか調べてください。

### 一覧画面の棚卸し(37画面)の要点
- カード見出し: 画面見出しは Card の title が担う(PageHeader 部品は無い)。見出しなし1(タスク一覧)。画面名(`routes/pageHierarchy.ts`・`routeManifest.ts`・`adminNavGroups.ts`)と不一致:
  「自分の月次勤怠/自分の有給/自分の代休/自分の特別休暇/自分の経費精算」(画面名は「月次勤怠/有給/代休/特別休暇/経費精算」)、「ロール一覧」(ロール管理)、「ユーザー一覧」(ユーザー)、
  「申請種別一覧」「グループ一覧」「所属変更一覧」「グループ種別管理」「経費区分一覧」、複数Cardの管理画面(有給休暇・特別休暇設定・代休設定・人事データ連携・一括操作・採番ルール設定)。
- 主操作: Card actions に置くのが14画面。文言は「新規作成」7・「新規登録」3・「新規申請」・「新規グループ」(テキストリンク)・「変更予約作成」・「ユーザーを作成」(カード本文の secondary ボタン)。
  主操作以外(CSV・関連画面へのリンク)は Card actions に Button とテキストリンクが混在。
- 一括操作: BulkActionBar 4画面(申請一覧だけフィルターの上)。勤怠の選択モードは別部品(§2.21 の対象外)。
- ページング: `components/Pagination` 14画面(左に「{total}件中 {c} / {p} ページ」、右に前後ボタン。番号なし。lastPage≤1 で非表示)。月次勤怠だけ独自のページャーで件数がページ内の件数。監査ログは件数を2か所に出す。
- モバイル: 表は `ui/table` の `overflow-x-auto` で横スクロール(列を隠す・カード型への切替は無い)。Card ヘッダーは sm 未満で縦積み。
- ルール: §2.1(主操作は右上)、§2.3(行内操作)、§2.20(検索フォーム)、§2.21(一括操作)にあるが、カード見出し・主操作の文言・ページングの表示・モバイルの表のルールは無い。

- 正データと派生データ: 画面の表示だけの変更。データ・API・イベントに影響しない。

- 理由: R1〜R10 の直し方は論点2〜7 の標準化の決定(詳細条件の見せ方・幅の決め方)と一体で、別々に直すと二度手間になる。前の変更セットには不具合と修正先を記録して追跡できるようにする。

### 論点2: カードの見出し
- 選択肢: A. 一覧画面の主となる Card の見出し = 画面名(`pageHierarchy.ts` の title)に必ず一致させる / B. 画面ごとに任せる
- 決定: A
- 細則:
  - 一覧画面は主となる Card を1つ持ち、その title を画面名にする(タスク一覧は「タスク一覧」を追加)。
  - 画面名の方を正とし、Card の見出しを合わせる。「自分の〜」は画面名(「有給」等)に合わせる。「ロール一覧」→「ロール管理」等、上の不一致はすべて画面名にする。
  - 1画面に複数の Card がある画面(本人の休暇画面の申請フォーム、管理画面の各セクション)は、2つ目以降の Card の見出しをセクション名にしてよい。ただし最初の Card の見出しは画面名にする。
    最初の Card がセクションしか持たない管理画面(有給休暇・特別休暇設定・代休設定・人事データ連携・一括操作・採番ルール設定)は、ページ上部の見出しが無くなるため、
    Card の上に画面名の見出し(`h1`、ui-design-system の見出しサイズ)を置く。
- 理由: 戻る導線(§2.26)・ナビの文言・見出しが同じ語であれば、今どの画面にいるかが一目で分かる。
- 未確定・要確認事項: なし

### 論点3: 主操作(新規作成など)と、その他の画面操作の置き場所
- 選択肢:
  - A. 主操作は Card の actions の右端に primary の Button で1つ。文言は「新規作成」に統一。その他の画面操作(CSV・関連画面への移動)は主操作の左に secondary の Button
  - B. 文言を「〇〇を作成」に(対象名入り)
- 決定: A
- 理由: 見出しが画面名(対象)を示すので、ボタンに対象名を重ねなくてよい。現状の多数派(7画面)で、§2.7(作成)に合う。テキストリンクとボタンが actions に混在しているのを Button にそろえる。
- 細則:
  - 文言の変更: 「新規登録」(備品・端末・外部連携設定)・「新規申請」(申請一覧)・「新規グループ」・「変更予約作成」(所属変更)→「新規作成」。社員一覧はカード本文の「ユーザーを作成」を actions の「新規作成」へ移す。
  - グループの「新規グループ」はテキストリンクから primary の Button(`asChild`+Link)にする。社員一覧の「外部ID・HR連携」、有給休暇の付与予定へのリンクは secondary の Button にする。
  - 端末・外部連携設定の「新規登録」はインラインのフォームを開閉するトグルで、開いている間は「閉じる」になる。開閉の挙動は変えず、閉じているときの文言だけ「新規作成」にする。
  - 主操作が無い画面は actions に何も置かない(承認・タスク・通知 等)。本人の休暇画面の「申請する」はフォームの送信で、主操作ではない(フォームのルール=変更セット`20261123-form-layout-standard`に従う)。
  - モバイル(sm 未満)では Card ヘッダーの既存の挙動(見出しの下に actions が回り込む)のまま。
- 未確定・要確認事項: なし

### 論点5: ページング
- 選択肢:
  - A. `components/Pagination` だけを使い、件数はその中(左の「{total}件中 {c} / {p} ページ」)だけに出す。前後ボタンのみ(番号なし)
  - B. ページ番号ボタンを足す
- 決定: A
- 理由: サーバーのページングで1ページ20件。業務の一覧は絞り込んでから見る使い方で、番号で飛ぶ必要が薄い。番号は幅390で収まらない。件数の二重表示(P5)と独自ページャー(月次勤怠)をなくし、表示を1種類にする。
- 細則:
  - 監査ログの上の「全N件 (c/pページ)」を削除する。
  - 月次勤怠の独自ページャーを `components/Pagination` に置き換える(total は月の総数。今の「ページ内の件数」表示の誤りもこれで直る)。
  - Pagination は表(またはリスト)の直下、Card の本文の末尾に置く。1ページしか無いときは出さない(現行どおり)。
  - モバイル: 現行の1行(左に件数、右に前後ボタン)のまま。件数の文言が長くて折り返すときは、件数を上・ボタンを下にする(`flex-wrap`)。
- 未確定・要確認事項: なし

### 論点6: 詳細条件(要否と見せ方)
- 要否:
  - 選択肢: A. 直接表示は4項目までとし、超える分を詳細条件にする(§2.20 現行) / B. 詳細条件をやめて全項目を常に表示 / C. 詳細条件を Sheet にする
  - 決定: A(現行の要否の基準を維持)
  - 理由: 備品(10項目)・監査ログ(5項目)・社員(6項目)は全表示すると表より検索欄が大きくなる。Sheet は結果を見ながら条件を変えられない(§2.20 の理由のまま)。
- 見せ方(R3・R5・R6・R10 の修正):
  - 選択肢: A. 「詳細条件」「検索条件をクリア」をひとまとまりにして末尾に置き、詳細条件の領域は枠付きのグリッドで出す / B. 現行のまま幅だけ調整
  - 決定: A
  - 細則:
    - `ListFilterBar` の末尾のボタンは1つのまとまり(`flex gap-2`)にし、項目の後ろに `ml-auto` で右寄せで置く(折り返すときはまとまりごと次の行の右端に行く。ボタンが1つずつ取り残されない)。
    - 「詳細条件」ボタンは `variant="secondary"` にし、開閉を示すアイコン(lucide の ChevronDown / ChevronUp)を付ける。件数表示「詳細条件(n)」は現行どおり。
    - 詳細条件の領域はフィルターバーの下に、枠付きの面(`rounded-md border bg-muted/40 p-3`)として出し、中は等幅のグリッド(`grid grid-cols-1 gap-3 @md:grid-cols-2 @3xl:grid-cols-3`。論点7のコンテナクエリ)にする。項目の幅はグリッドに任せる(`filterWidth` を使わない)。
- 未確定・要確認事項: なし

### 論点7: 狭い本文幅での項目の幅(R4)
- 選択肢:
  - A. フィルターバーをコンテナ(`@container`)にし、項目の幅を「画面幅」ではなく「フィルターバーの幅」で決める(Tailwind v4 のコンテナクエリ)
  - B. 画面幅の区切りを `md:`・`lg:` に上げる
- 決定: A
- 理由: 管理画面は管理メニューの分だけ本文が狭く、画面幅では本文の幅が分からない。コンテナクエリなら、どのレイアウトに置かれても本文の幅で揃う。
- 細則: `ListFilterBar` の外側に `@container`。`filterWidth` を `keyword: 'w-full @xl:w-72'`、`select: 'w-full @xl:w-44'`、`yearMonth: 'w-full @xl:w-48'`、`dateRange: 'w-full @xl:w-72'` にする
  (フィルターバーが 36rem 未満なら全項目が全幅で縦に並ぶ)。申請一覧の種別は `filterWidth.select` にそろえる。監査ログの対象タイプは詳細条件のグリッドに任せる(論点6)。
  端末のチェックボックス行は `h-9`。
- 未確定・要確認事項: なし

### 論点8: モバイル・狭い幅の表示
- 主軸タブ(R1・P1):
  - 選択肢: A. 折り返して全タブを見せる / B. 横スクロールのまま、右端にフェードで続きを示す / C. sm 未満はセレクトに切り替える
  - 決定: A
  - 理由: タブは5つ以下(§2.20)で、折り返せば全タブと件数が常に見える。B は指で横に送らないと件数が見えない。C はタブと見た目が変わり、件数を見比べにくい。
  - 細則: `ListQueueTabs` の TabsList を `h-auto flex-wrap` にし、横スクロール(`overflow-x-auto`)をやめる。
- 表(P4):
  - 選択肢: A. 表は横スクロールのまま、件名などの主な文字列の列だけ折り返す / B. sm 未満はカード型のリストに切り替える / C. sm 未満で一部の列を隠す
  - 決定: A
  - 理由: 業務の一覧は列を見比べる用途が主で、カード型は全37画面分の別表示が要り費用が大きい。列を隠すと必要な情報が見えなくなる。横スクロールのまま、件名が折り返さずに右端の列を押し出す問題(1280でも発生)だけを直す。
  - 細則: `ui/table.tsx` の TableCell の一律 `whitespace-nowrap` は残し、各一覧の件名・タイトル・名称の列(1画面1列。例: 申請一覧のタイトル、タスク一覧のタイトル)に `whitespace-normal min-w-48` を付ける。
- 管理画面の本文幅(P3):
  - 決定: 管理メニューの縦のサイドバーは `lg` 以上だけに出し、`lg` 未満は現在 `sm` 未満で使っている表示(`AdminLayout.tsx:89` のメニューボタン)を使う。
  - 理由: 640〜1023px でアプリのサイドバーと管理メニューが並ぶと本文が約250pxになり、フィルター・表がほぼ使えない。
- 長い文字列(P2): 監査ログのイベント種別などの英数字の識別子は `break-all` で折り返す。
- 期間の入力(R2): `DateRangePicker` の表示 span に `min-w-0` を付け、狭いときは省略表示(`truncate`)させる。
- 未確定・要確認事項: なし

## 仕様確定事項(まとめ)
1. 部品:
   - `ListFilterBar`: 外側 `@container`。末尾ボタンのまとまり(`ml-auto flex gap-2`)。「詳細条件」は secondary+開閉アイコン。詳細条件の領域は `rounded-md border bg-muted/40 p-3` の等幅グリッド(`grid-cols-1 @md:grid-cols-2 @3xl:grid-cols-3`)。
   - `filterWidth`: `@xl:` 基準(論点7)。
   - `ListQueueTabs`: 折り返し(`h-auto flex-wrap`)、横スクロールなし。
