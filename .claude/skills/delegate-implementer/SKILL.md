# implementerへの委譲指示の組み立て

implementerは指示に書かれていないことを推測で埋めるか、気づかずに素通りする。受け手は
「欠けている」ことに気づけないため、欠けを防げるのは送り手(委譲元)だけ。指示を送る前に
下のチェックリストを上から確認し、該当する項目は指示文に書く(該当しない項目は書かなくてよい)。

根拠は`docs/delegation-reviews/`の「委譲元の指示不足」行(2026-09〜10)。新しい種類の指示不足が
レビューで見つかったら、ログに書くだけでなくこのファイルの該当節に1行足す。

## 指示文のテンプレート

```text
目的: <何を実現するか1〜2文>
仕様の出典: docs/changesets/<フォルダ>/spec.md の <論点・決定番号>(実装スコープの正)
対象ドメイン / 従うスキル: <App\Domain\... / .claude/skills/...>
参照する既存実装: <パス>(<何を写すか>)
作成・変更するファイル: <パス一覧。新規クラスは名前確定済み>
変更しないもの: <触ってはいけないファイル・既存の振る舞い>
適用範囲: <このルールを適用する経路 / 適用しない経路>
欠落・境界の扱い: <入力が無いとき・0件・境界日など、決めた扱い>
テスト: <追加するテストとケース、期待値とその根拠、前提(シーダー・キュー等)、実行するコマンド or 実行しない>
報告: 変更ファイル一覧(git status --short)、追加テスト、未解決の論点。コミットしない。
```

## チェックリスト

### 1. 適用範囲(経路)— 最も多い指示不足

- [ ] 新しいルール・値が**どの経路で使われるか**を全て列挙したか(例: 承認・再生/移行・作り直し・
      passThroughの写し・照合)。「〜だけ差し替える」「`$converted`から集める」のように1経路に限定する
      書き方をしていないか。限定するなら、他の経路で**使わない**理由も書く。
- [ ] 発生日時・利用開始日のように**複数経路を横断する値**は、経路ごとに差し替えさせず「入力の段階で
      一度だけ決め、全経路がそれを読む」形を指示したか。
- [ ] 既存の集約・規則と同じ結果を保証させる場合、**当てはめる既存規則を全部名指し**したか
      (例: 確定時・付与時・消化の取消・付与の変更・付与の取消 → `cancelUsage`・`changeGrantAmount`・
      `revokeGrant`)。「現行と同じに」だけでは一部しか実装されない。

### 2. 欠落・境界の扱い

- [ ] 「対応する旧データ・イベントが無いとき」「列がNULLのとき」「0件のとき」の値の取り方を決めて書いたか
      (例: 旧版イベントが無ければ行の`manual_override_at`・`updated_at`を使う)。決めていなければ
      委譲前に決める。仕様判断が要るならユーザーに確認する。

### 3. 命名・配置

- [ ] 新規クラス・ファイル名を委譲前に`Glob`/`Grep`で衝突確認し、確定した名前を渡したか。
- [ ] 同じ処理を複数の文脈に置く場合、共有の置き場所(例: `App\Domain\Leave\Support`、抽象基底+薄い具象)
      を指示したか。指示しないと文脈ごとに複製される。
- [ ] 文脈の境界(原則15)上、書いてよいテーブル・読んでよいテーブルを示したか。

### 4. DB・破壊的操作

- [ ] Projectorを新設・変更する場合、同じテーブルを埋める既存Projectorと**NOT NULL列**を確認し、
      埋めるべき列を指示したか。
- [ ] 削除・TRUNCATE・作り直しの対象一覧を作らせる場合、**除外するもの**(イベントストア本体、参照マスタ、
      認証情報、直接更新の正データ)を指示したか。

### 5. テスト

- [ ] ドメイン計算の**期待値とその算出根拠**(どの入力からどの出力になるか)を指示側で示したか。
      implementerに期待値を組み立てさせると、存在しない条件のデータを作って辻褄を合わせることがある。
- [ ] 日付・日数の期待値は、途中の並び(例: 入社日+6・18・30か月の付与予定日)も併記したか。結果の値だけを書くと、
      委譲元の計算の誤りに誰も気づけない(入社日を変えても付与予定日が変わらない例を、変わる例として書いた)。
- [ ] テストの状態はCommand/イベント経由で作らせ、ReadModelへの直接書き込みをさせない(原則2)と書いたか。
- [ ] テストが依存する前提(シーダーの再実行、キューの実行方法=`QUEUE_CONNECTION`、日付・時刻の固定など)
      を書いたか。
- [ ] 権限・閲覧可否などの前提が複数のケースに効く場合、特定のケースの注記ではなく全ケース共通の前提として書いたか
      (例: 他人の月次を見るには`attendance.read`のglobalが要る、を1ケースにだけ書いて他のケースで漏れた)。
- [ ] e2eを書かせる場合、操作の後はAPIの完了(`waitForResponse`や画面上の結果)を待ってから次の操作に進むこと、
      期待値は変更セットの定義(例: どの操作でどのバッジが付くか)に従うことを書いたか(操作直後のEscで未保存の
      確認が出て閉じられない、Overrideで「変更あり」が付くと誤って期待する、が起きた)。
- [ ] serial実行のe2eにテストを足させる場合、前のテストで状態が変わる行(付与済みにした行など)を対象にしない
      こと、対象はAPIで条件に合う行を探して選ぶことを書いたか。
- [ ] backendとfrontendを並行で委譲するときは、APIの応答の形を、包み(`{ data: ... }`)まで含めて両方の指示に同じ文で
      書いたか(包みを書かずに形だけ書いたため、backendは包み、frontendは包みを外さずに受け取り、画面に「NaN」が出た)。
- [ ] PRを出す前に、backendをCIと同じ条件で全件流したか。手順は`cp .env.example .env && php artisan key:generate && php artisan test`で、後で`.env`と`database/database.sqlite`を消す。
      `./vendor/bin/phpunit`はphpunit.xmlの値(in-memoryのsqlite・同期キュー・APP_KEYなし)で動き、CI(ファイルのsqlite・databaseのキュー・APP_KEYあり)と違う。
      そのため、起動の時の行の作成やキューの前提のずれを見逃した(PR#121)。
- [ ] migrationを足したときは、down()を、データ移行(後続のmigration)の後の状態で確かめるテストがあるか(CIの`migrate-mysql`は、`migrate`の後に`migrate:rollback`を行う)。
- [ ] frontendの型チェックは`npx tsc -p tsconfig.app.json --noEmit`を指定したか(ルートの`tsconfig.json`は
      参照だけなので、`npx tsc --noEmit`では何も検査されない)。
- [ ] コマンドの出力や画面の文言を変える作業では、その文言を期待しているテストとe2eを`grep`で探して直すことを書いたか
      (roll-schedulesの出力を変えて、e2eの期待値が古いまま残った)。
- [ ] backendのテストは`./vendor/bin/phpunit`で実行させる。`backend/.env`があると`php artisan test`は開発用のDBに対して動き、
      DBを壊すことがある。e2eのために`.env`を作ったら、検証の後に消す。
- [ ] frontendのテストでログインユーザーを差し替えさせる場合、対象のテストファイルが`useAuth`を`vi.mock`しているか、
      `AuthContext.Provider`で包んでいるかを指示前に確かめ、その方式で指示したか(storyの書き方をそのまま指示したら、
      `vi.mock`のファイルでは効かなかった)。
- [ ] テストを実行させるか、させるならコマンドと対象(例: `cd backend && php artisan test tests/Unit/...`)を
      書いたか。実行させない場合は委譲元で実行する。

### 6. 報告

- [ ] 報告に変更ファイル一覧(`git status --short`)を含めさせたか(無関係ファイルの混入・途中状態の
      検出用)。委譲元は一覧にあるファイルだけをコミットする。

## モデルの選択

- 既定は定義どおり`haiku`。
- 次のいずれかに当たる場合は、Agent呼び出しで`model: sonnet`を指定する。
  - 複数の入力経路をまたぐ変換、既存の集約・規則と同じ記録になることを保証する状態機械・作り直し処理。
  - 同じタスクでhaikuが途中停止した、または同じ種類の差し戻しが2回続いた。
- sonnetにした場合は、`delegation-review`のログのmodel列に`sonnet`、対応列に上げた理由を書く。
- 上げる前に、まず指示不足(上のチェックリスト)でないかを疑う。指示で解決するならモデルは上げない。

## 委譲後

- 完了レビューと記録は`delegation-review`に従う。手戻りの原因が指示不足なら、このファイルの該当節に追記する。
