# データ補正・データ移行

ReadModel(Projection)だけを書き換える補正は、どんな場合も行わない(ルート`CLAUDE.md`
設計原則2)。補正・移行は必ずイベント履歴(`stored_events`)側で行い、Projectionはリビルドで
反映する。

**常に、できる限り過去の履歴そのものを修正する。** 目的は、`stored_events`が「最初から正しい
イベント構成で記録されていた」状態になり、コードが旧系統の読み替え・移行イベント・補正イベントを
持たずに済むこと(イベント構成をできる限りシンプルに保つ)。方法は次の3つで、上から順に選ぶ。

1. **部分的な書き換え**: 既存イベントのpayloadの書き換え・誤って記録されたイベントの削除。
   少数のイベントを直す補正に使う。
2. **`stored_events`の作り直し**: 旧イベント列全体から、新しいイベント構成のイベント列を決定的に
   生成し直し、`stored_events`を置き換える。**データ移行(集約の分割・統合、イベントの改名・分割・
   統合、集約IDの付け替え、欠落した事実の補完=過去への挿入)は必ずこの方法で行う。** 移行イベント
   (`*.migrated`等、今の時点に「現在の状態」を追記するイベント)は作らない。
3. **補正イベントの追記**: 過去の事実(いつ・誰が・何をしたか)を既存のイベント・データから
   機械的に決められない場合だけ。採らなかった1・2の理由を変更セットに明記する。

## 判断手順

データ補正・データ移行の話が出たら、変更セット(`changeset`スキル)の「仕様検討」に論点
「補正方法」(移行なら「イベント構成の作り直し」)を立て、次を書く。

1. **対象**: 対象のイベント(`event_class`・集約・`event_properties`のキー)と件数。
2. **変換規則**: 旧イベント1件ごとに、新しいどのイベント(0件・1件・複数件)になるか、集約ID・
   payload・発生日時をどう決めるかの対応表。新しいイベント構成で不要になる旧イベントクラス・
   Projectorの旧系統の読み替え・移行用コマンドを「削除するもの」として列挙する。
3. **再現性**: 変換後のイベント列をリビルドすると正しい最終状態になること(後続イベントとの順序を
   含む)。
4. **過去の事実が決められない部分**: あれば、その部分だけ方法3にする理由。

書き換えは「事実を新しい構成で正しく記録し直す」ためだけに使う。利用者が行った操作や承認など
業務上の事実そのもの(設計原則13の承認イベント等)を消したり書き換えたりして状態を巻き戻す目的では
使わない(それは差戻し・取消など専用のCommand/Eventで行う)。

**本番での実行にはユーザーの明示的な許可を得る**: 変換規則(対象・件数・変換後の形)と試し実行の
結果を示したうえで、AskUserQuestion等で許可を得る。許可の日時と内容を変更セットの「レビュー履歴」に
記録する。

## `stored_events`の作り直しの進め方

- **変換は運用コマンドとして実装する**: `backend/app/Console/Commands/`のコマンドで、旧イベント列を
  読み、変換規則(コードとテストで固定)に従って新しいイベント列を作る。手作業のSQLは使わない。
- **id・版を振り直す**: 新しいイベント列を元の発生順(元の`id`順。1件を複数件に分けた場合はその
  並び)に並べ、`stored_events.id`を振り直し、集約ごとに`aggregate_version`を1から連番にする。
  `event-sourcing:replay`は`id`順に再生するため、これで過去への挿入・分割も正しい順で再現される。
  `created_at`(発生日時)は元のイベントの値を引き継ぐ。
- **新しい表に書いてから入れ替える**: 新しいイベント列は別の表(例`stored_events_rebuilt`)に書き、
  検証が通ってから`stored_events`と入れ替える。元の表はバックアップとして残す(表名を記録)。
  `stored_events.id`を参照している列(Projectionの`source_event_id`、補正ログ等)とスナップショットは
  リビルド・削除の対象として列挙する。
- **試し実行を既定にする**: 既定は変換結果の件数・旧→新の対応の一覧を出すだけ。入れ替えは明示的な
  オプション指定時のみ。
- **検証を手順に含める**: 入れ替え前に、新しいイベント列で全Projectorをリビルドした結果と、移行前の
  ReadModel(または移行前に取った基準値)を比較するSELECT文・コマンドを用意し、差分が「変換規則で
  意図した差」だけであることを確認する。
- **コードの整理まで含める**: 作り直し後に不要になる旧イベントクラス・旧系統の読み替え・移行用の
  コマンドは同じ変更セットで削除する(`config/event-sourcing.php`の別名も)。リリースは
  「作り直しの実行」と「旧系統を削除したコードの配備」を1つの手順にする。

## 部分的な書き換えの安全手順

- **運用コマンドとして実装する**: 既存の`NormalizeAttendanceCalculationEventsCommand`等を前例に、
  対象の抽出条件・書き換え後の値をコードとテストで固定する。
- **試し実行(dry-run)を必須にする**: 既定は対象イベントのID・修正前後の値の一覧を出力するだけ。
- **修正前の内容を残す**: 本実行前に`stored_events`のバックアップを取り、修正したイベントのIDと
  修正前のpayloadを補正ログに残す。
- **冪等にする**: 再実行しても結果が変わらない。
- **リビルドと検証までを1つの手順にする**: 再生成が必要なProjectionとその順序、確認のSELECT文を
  変更セットに書く。
