# タスクブリーフィング

大きめのタスクを始める前に、以下のテンプレートを埋めて提示する。ここで作業範囲を
確定させてから着手することで、探索範囲・実装範囲・報告範囲が広がりすぎるのを防ぐ。

```
目的:
<1〜2文。何を実現するか>

確認対象:
<既存実装の読解が必要なパス。ディレクトリ単位で絞る(例: app/Domain/Attendance)>

参考実装:
<構造を真似る既存の類似実装(あれば)>

実装対象:
<変更・追加するファイル/機能を列挙>

対象外:
<今回やらないこと(フロント/バック、承認、通知、無関係なリファクタリング等)を明示する>

制約:
<従うべき既存規約・追加しない依存関係など>

検証:
<実行するテストコマンド>

ドキュメント:
<今回の変更でユースケースが追加・変更されるか確認する。対象がある場合はdocs/配下の
該当ファイル(docs/README.mdの目次で該当章を特定)を列挙し、実装対象に含める。
対象が無い場合も「変更なし」と明記する(省略しない)>

進め方:
対象範囲だけを調査し、必要最小限の変更を行う。
実装中の長い説明は不要。
完了時に変更ファイル・実装内容・テスト結果だけ報告する。
```

## 運用ルール

- 「確認対象」は具体的なディレクトリ・ファイルパスで書く。「関連しそうな箇所」のような
  曖昧な範囲指定はしない。範囲が本当に分からない場合のみExploreサブエージェントに
  範囲特定自体を委譲し、その結果を「確認対象」に反映してから本作業に入る。
- 「対象外」は省略しない。書かないと、承認処理・通知・リファクタリングなど頼まれていない
  作業まで手を広げてトークンを消費しやすい。
- 「ドキュメント」も省略しない。実装対象のユースケースがdocs/06〜17等の既存記述と
  食い違う状態のまま完了報告しない。新しいユースケース(UC-番号)を追加した場合・既存の
  ユースケースの手順やイベント名を変更した場合は、該当ドキュメントを実装と同じタスク内で
  修正する。修正不要と判断した場合も、その判断をブリーフィングまたは完了報告に明記する
  (ドキュメントが古いまま放置されるのを防ぐため)。
- ブリーフィングを作ったら、そのままサブエージェント(Agentツール)への委譲プロンプトとして
  再利用する。ブリーフィングを作った後にメインの会話で同じ調査を繰り返さない。
- ブリーフィング自体は数行〜十数行に収める。ブリーフィングを作ること自体が調査コストに
  ならないよう、既に分かっている情報だけで埋める(このステップのために追加の探索を
  増やさない)。
