# 委譲レビューログ

flow-officeのCLAUDE.mdが定める「委譲したエージェントの完了レビューを徹底する」
「作業の区切りごとにタスク割り当て自体の妥当性を振り返る」を、記憶ではなく
ファイルとして残すためのスキル。

## いつ使うか

- Agentツールで`investigator`または`implementer`(将来追加される安価モデル
  エージェントを含む)に調査・実装を委譲し、その完了報告をレビューしたとき、
  毎回このスキルに沿ってログを1エントリ追記する。
- 作業の区切り(タスク完了・PR作成前など)で、その回のタスク割り当て自体の
  妥当性を振り返ったときも追記する。

## 記録先

`docs/delegation-reviews/YYYYMM.md`(月次ファイル。存在しなければ新規作成し、
下記テンプレートのヘッダーを書く)。

```markdown
# 委譲レビューログ YYYY-MM

| 日時 | Agent | model | 依頼内容(要約) | 達成状況 | レビュー結果 | 対応 |
|---|---|---|---|---|---|---|
```

## エントリの書き方

1行=1委譲。以下の列を埋める。

- **日時**: `YYYY-MM-DD HH:MM`(分かる範囲でよい)
- **Agent**: `investigator` / `implementer` / その他
- **model**: そのAgent定義(`.claude/agents/*.md`のfrontmatter)に設定されている
  モデル名(例: `haiku`)。委譲前に該当ファイルを確認し、想定通りの安価モデルに
  なっているかもここで確認する。ズレていれば「対応」列に是正内容を書く
- **依頼内容(要約)**: 何を委譲したか(ドメイン名・スキル名・対象ファイルなど)を
  1行で
- **達成状況**: エージェントの自己申告(`達成`/`部分達成`/`未着手`)をそのまま転記
- **レビュー結果**: 上位モデルが実際に確認した結果。「該当ファイルが存在するか」
  「テストが本当に通っているか」等、自己申告を鵜呑みにせず検証した内容と結論を書く。
  問題があれば具体的に(例: 「storyファイルが未作成」「テストは通っているが
  仕様のエッジケース未対応」)
- **対応**: 問題があった場合の是正内容。原因が委譲時の指示不足・スキル記述の
  曖昧さ等であれば、該当する`.claude/skills/*/SKILL.md`や`.claude/agents/*.md`を
  その場で更新し、この列に「〜を更新」と記す。仕様判断が絡み自己解決できない
  場合はユーザーに報告した旨を書く

## タスク割り当ての妥当性振り返り(区切りごと)

上記の委譲単位のログとは別に、作業の区切りごとに以下を1エントリとして
同じ月次ファイルの末尾に追記する(表形式ではなく箇条書きでよい):

```markdown
### 振り返り: <区切りの名前>(YYYY-MM-DD)

- 本来investigator/implementerに委譲できた定型作業をメインの会話が直接処理
  していないか: <あり/なし、詳細>
- 設計判断・仕様確認が必要な作業を安価なモデルに丸投げしていないか: <あり/なし、詳細>
- 是正: <次回からの割り当て変更、または更新したファイル>
```

## 注意

- ログにソースコード全文・diff全文を貼らない(要点のみ)。
- このログ自体は事後の振り返り用の記録であり、`docs/changesets/`の仕様検討
  ドキュメントを代替するものではない。
