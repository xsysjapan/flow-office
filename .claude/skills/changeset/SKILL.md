# 変更セット駆動開発(ドキュメント駆動開発)

大きめのタスクは「コードを書く前に、変更セットというドキュメントの上で仕様を決め切り、
ユーザーの承認を得てから実装に入る」の2段階で進める。実装を始めてから仕様の曖昧さに
気づいて手戻りするコストを避けるため、曖昧さは変更セットの段階で潰す。

## 全体の流れ

1. **変更セットフォルダを作る**(このスキルの本体)。`spec.md`の「ステータス」を
   `検討中`にし、`docs/changesets/README.md`の一覧にも追加する
2. **仕様検討を行い、変更セットに決定事項を書き込む**(曖昧さを残さない)
3. **ユーザーに変更セットを提示しレビューを受ける**。提示時に「ステータス」を
   `レビュー中`に更新する(必要なら往復して仕様検討を更新する)
4. ユーザーの承認を得たら「ステータス」を`実装中`に更新してから実装に着手する
   (既存の`add-*`系スキル等はこの段階で通常どおり使う)
5. 実装完了後、変更セットに実装結果(実際のコミット・変更ファイル)を追記し、
   「ステータス」を`完了`に更新して閉じる。`docs/changesets/README.md`の一覧も
   `完了`に更新する

「ステータス」は必ずこの4値(`検討中`/`レビュー中`/`実装中`/`完了`)のいずれかとし、
完了済みかどうかが`spec.md`単体でも一覧でも一目で分かる状態を保つ。

ステップ2〜3を飛ばして直接実装を始めない。ユーザーが明示的に「仕様検討は不要、
すぐ実装して」と指示した場合のみ、変更セット作成を省略してよい。

## 1. 変更セットフォルダを作る

```
docs/changesets/YYYYMMDD-変更名/
  spec.md          # このスキルの本体(テンプレートは下記)
  assets/           # モック画像・ワイヤーフレーム・サンプルデータ等(任意)
```

- `YYYYMMDD` は変更セット作成日(今日の日付)。
- `変更名` は英数字・ハイフンの短い識別子(例: `20260829-expense-multi-currency`)。
  日本語でも良いが、ファイルシステムで安全な文字に限る。
- 同じ変更を複数日にまたがって検討する場合もフォルダ名(=作成日)は変えない。
- モック画像・スクリーンショット・サンプルCSV等は`assets/`に格納し、`spec.md`から
  相対パスで参照する。

## 2. `spec.md` テンプレート

```markdown
# <変更名>

ステータス: 検討中

## 変更要望(原文)
<ユーザーから実際に受け取った依頼文。要約せずできるだけそのまま引用する>

## 背景・目的
<なぜこの変更が必要か。1〜3文>

## 現状(As-Is)
<関連する既存の実装・ドキュメント(docs/06〜17等のUC-番号を含む)・DBテーブルを
具体的なファイルパス・章番号付きで列挙する>

## 仕様検討

論点ごとに、選択肢を洗い出してから決定する。「決定」と「理由」は必須(空欄禁止)。
検討事項が1つしかない場合も見出しは残す。

### 論点1: <論点の名前>
- 選択肢:
  - A. <選択肢と、選んだ場合の影響>
  - B. <選択肢と、選んだ場合の影響>
- 決定: <A or B、あるいは折衷案>
- 理由: <なぜその決定に至ったか>
- 未確定・要確認事項: <ユーザー確認が必要な場合はここに明記し、仮決定である旨も書く>

### 論点2: ...

## 仕様確定事項(まとめ)
<上記の検討結果を、実装者がそのまま読めば迷わないレベルの粒度で箇条書きにする。
入力項目・状態遷移・バリデーションルール・権限・表示条件・エラー時の挙動など、
曖昧さが残らないように具体的に書く(「よしなに」「適宜」等の表現を使わない)>

## 対象外
<今回やらないこと(隣接する機能・将来対応・別ドメイン等)を明示する>

## ドキュメントへの影響
<docs/配下で新規追加・修正が必要なファイルを列挙する(docs/README.mdの目次で該当章を
特定)。対象が無い場合も「変更なし」と明記する(省略しない)>

## モック・アセット
<assets/配下に置いたファイルへのリンクと、それぞれが何を表すかの説明。無ければ「なし」>

## 実装対象
<変更・追加するファイル/機能を列挙。ディレクトリ単位まで具体化する>

## 検証方法
<実行するテストコマンド・確認手順>

## レビュー履歴
<ユーザーとの往復で仕様が変わった場合、変更点と日時を追記する。初版のみなら「初版」>

## 実装結果
<実装完了後に追記する。変更ファイル一覧・実行したテスト結果・コミットハッシュ等。
実装着手前は「未着手」と書いておく>
```

## 運用ルール

- **仕様検討セクションを一番厚く書く**。選択肢を並べずにいきなり結論だけ書かない。
  複数の実現方法がありうる論点(データ構造・状態遷移・UI挙動・権限・エラー処理など)は
  必ず「選択肢→決定→理由」の形にする。
- 「未確定・要確認事項」を作ったまま実装に進まない。ユーザーに確認し、確定させてから
  次のステップ(ステップ3のレビュー提示)に進む。
- 変更セットが完成したら、その内容をそのままユーザーに提示して確認を取る。ユーザーから
  修正依頼が来たら`spec.md`を直接更新し、「レビュー履歴」に差分を残す(消して書き直さず、
  検討の経緯が追えるようにする)。
- 「ドキュメントへの影響」は省略しない。新しいユースケース(UC-番号)を追加する場合・
  既存ユースケースの手順やイベント名を変更する場合は、実装と同じタスク内で
  `docs/`本体も修正する。修正不要と判断した場合もその判断を明記する。
- 「対象外」も省略しない。書かないと、承認処理・通知・リファクタリングなど頼まれていない
  作業まで手を広げてトークンを消費しやすい。
- 調査(現状把握・関連ファイル特定)が広範囲に及ぶ場合はExploreサブエージェントに委譲し、
  結果だけを「現状(As-Is)」に反映する。仕様検討そのもの(選択肢の洗い出し・決定)は
  委譲せずメインの会話で行う(判断の質を保つため)。
- 実装段階に入ったら、`spec.md`の「実装対象」と「仕様確定事項」を実装スコープの正とする。
  ここに書かれていない仕様変更が実装中に必要になった場合は、先に`spec.md`を更新してから
  コードを直す(コード側だけで仕様を作らない)。
- 実装完了時は`spec.md`の「実装結果」を埋めてから完了報告する。変更セット自体は
  完了後も履歴として残す(削除しない)。
- 変更セットの本文自体は簡潔に保つ(仕様検討の厚みと、無関係な前置きの長さは別)。
  既に分かっている情報の言い換えや、実装で自明な手順の説明に紙面を使わない。
- `docs/changesets/README.md`には全変更セットの一覧表(フォルダ名・タイトル・ステータス)
  を持たせ、フォルダを作成した時点で行を追加する。ステータスが変わるたび
  (`spec.md`側の更新と同時に)この一覧表も更新し、完了済みの変更セットが一覧からすぐ
  分かるようにする。
