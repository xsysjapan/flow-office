# 業務ルールと文脈間連携のテスト

ルート`CLAUDE.md`設計原則16の具体的な進め方。目的は「画面を操作しなくても、業務ルールと文脈間の連鎖が
想定どおり動くことをテストで確かめられる」状態にすること。E2E(Playwright)はコストが高いため主要導線の確認に
留め、網羅はこのスキルのテストで行う。

## テストの種類と使い分け

| 種類 | 置き場所 | 何を確かめるか | 使ってよいもの |
|---|---|---|---|
| ルールのテスト | `tests/Unit/<Domain>/` | 1つの業務ルール(Aggregateの不変条件、計算・判定クラス)の正常・境界値・異常 | SQLite+Eloquent・Laravelアプリの起動も可。ただし対象ルールだけを直接呼ぶ |
| シナリオテスト | `tests/Feature/<Domain>/` | 1つのユースケースの操作(API呼び出し、またはCommandのdispatch)から始まる連鎖全体で、関係する**全文脈の状態**(ワークフロー/業務の申請/残数/勤怠など)とイベントが想定どおりになるか | SQLite+Eloquent、HTTP・CommandBus |
| E2E | `frontend/e2e/` | 主要導線が画面から通るか | 最小限 |

- UIの表示・操作に依存しない(APIのレスポンス・DBの状態・記録されたイベントで検証する)。
- シナリオテストは「誰が・何を操作したら・どの文脈が・どの状態になるか」を1テストで通して確認する。例(休暇):
  申請→承認→取消、申請→差戻し→再提出→承認、承認不要での申請、まとめ申請、締め済みの日、残数不足、同日の衝突、
  管理者による取消。各ステップの後で、ワークフロー・休暇申請・消化記録/残高・勤怠(休暇ビュー・日次計算)を確認する。
- 失敗系(業務ルール違反で連鎖が取り消される)は、エラーが返ることに加え、**どの文脈の状態も変わっていない**ことを確認する。
- 冪等性・Reactorの独立性: 同じイベントを2回処理しても結果が同じこと、ワークフロー取消⇔業務取消のような双方向の
  連鎖が二重に処理されないことをテストする。
- リビルド: ReadModelを空から再生成しても同じ状態になることを、代表的なシナリオの後で確認する。
- 実際の画面で起きた不具合は、まずそれを再現するシナリオテストを書いてから直す(回帰の防止)。

## テストしやすい書き方
- 業務ルールはHandler・Projector・Controllerに直接書き込まず、Aggregateまたは判定・計算のクラスに置く
  (privateメソッドに閉じ込めない)。ルールのテストで直接呼べる単位にする。
- 設定値・「今日」の日付は引数で渡せるようにする(テストで値を変えられるように)。
- 参考: `backend/app/Domain/PaidLeaveAccount/Aggregates/PaidLeaveAccountAggregate.php` と
  `backend/tests/Unit/PaidLeaveAccount/PaidLeaveAccountAggregateTest.php`、
  `backend/app/Domain/PaidLeaveAccount/Support/AllocationPlanner.php`。

## 変更時の基準
- 業務ルールを追加・変更したら、そのルールのテストを追加・更新する。
- 文脈をまたぐ処理(Reactorの追加・変更、イベントの追加)をしたら、その連鎖を通すシナリオテストを追加・更新する。
- 既存コードを触るときは、触った範囲の業務ルール・連鎖からテストを補う。補いきれない場合は変更セットの「対象外」に
  残課題として明記する。
